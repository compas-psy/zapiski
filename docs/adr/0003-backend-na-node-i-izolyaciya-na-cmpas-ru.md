# ADR-0003. Бэкенд на Node/Fastify и правила изоляции на сервере cmpas.ru

* Статус: принято
* Дата: 2026-08-09
* Автор: CTO
* Отклонение от: `docs/spec/README.md` §2.2 («Облако КОМПАС — Rust (axum) или Go»)

## Контекст

ЗАПИСКИ разворачиваются на **действующем production-сервере cmpas.ru**, где уже
работает КОМПАС.Дневник. Это не пустая машина. На ней:

* `/var/www/cmpas.ru` — Next.js в Docker Compose, приложение на порту **3000**,
  postgres без проброса на хост, postfix-мейлер на порту **25**;
* `/var/www/moments.cmpas.ru` — статический vhost;
* nginx с `sites-available`/`sites-enabled`, TLS через certbot.

Главный риск проекта на этом этапе — не выбор языка бэкенда, а **уронить
работающий Дневник**. Любое решение подчинено этому.

## Решение

### Язык бэкенда

KompasCloud — **Node 22 + Fastify + PostgreSQL**, а не Rust/axum или Go.

Обоснование: бэкенд ЗАПИСОК по замыслу ТЗ (§4.1) — «тупая труба» для
**зашифрованных** чанков. Zero-knowledge (§2.1.5) означает, что сервер не имеет
доступа к содержимому и не выполняет над ним никакой логики: он хранит блобы,
версии и CRDT-апдейты, не понимая их. Вычислительно это I/O, а не CPU, — выигрыш
Rust здесь не материализуется. При этом Node даёт переиспользование **того же
кода протокола и тех же типов**, что и клиент (`@zapiski/core`), то есть один
контракт синка вместо двух его реализаций, расходящихся во времени.

Прикладной эффект: типы протокола объявлены один раз в `@zapiski/core/sync` и
импортируются и клиентом, и сервером. Рассинхрон протокола становится ошибкой
компиляции.

### Изоляция от Дневника (обязательные инварианты)

Нарушение любого из пунктов — блокирующий дефект:

1. **Отдельный домен** `zapiski.cmpas.ru`, отдельный vhost, отдельный docroot
   `/var/www/zapiski.cmpas.ru`. Vhost Дневника не читается и не редактируется.
2. **Отдельный порт.** API слушает **3100**. Порт 3000 (Дневник) и 25 (почта)
   не трогаются.
3. **Отдельный стек Compose**, отдельный project name `zapiski`, отдельные
   имена контейнеров (`zapiski-api`, `zapiski-postgres`), отдельные тома.
   `docker compose down` в одном каталоге не может задеть другой.
4. **Отдельная база.** Свой контейнер postgres без проброса порта на хост.
   К базе Дневника подключений нет ни одного.
5. **nginx только добавляется.** Провижн создаёт свой файл в `sites-available`,
   делает симлинк, запускает `nginx -t` и перезагружает конфиг **только при
   успехе**; при провале — симлинк снимается, `sites-enabled` остаётся в заведомо
   валидном состоянии. `reload`, никогда не `restart`.
6. **certbot строго `-d zapiski.cmpas.ru`.** Сертификат Дневника не
   переоформляется. Провал certbot оставляет ЗАПИСКИ на HTTP и не влияет на
   cmpas.ru.
7. **Почта.** Magic-link отправляется через уже существующий postfix
   (`ALLOWED_SENDER_DOMAINS: cmpas.ru`) — новых почтовых сервисов не заводим,
   SMS не используется нигде (§5.5 ТЗ, прямой запрет).

Эти правила реализованы в `deploy/` и в workflow `provision-zapiski.yml` /
`deploy-zapiski.yml`, каждое — с комментарием, ссылающимся на пункт этого ADR.

## Последствия

**Плюсы**

* Один контракт синка на клиент и сервер, проверяемый компилятором.
* Развёртывание повторяет уже проверенный на этом сервере паттерн
  (`deploy-moments.yml` / `provision-moments.yml`), а не изобретает новый.
* Откат ЗАПИСОК = остановка своего стека и снятие одного симлинка. Дневник об
  этом не узнаёт.

**Минусы**

* Node на порядок прожорливее Rust по памяти на соединение. Для blob-синка с
  ожидаемой нагрузкой раннего этапа это несущественно; при росте websocket-
  соединений вопрос пересматривается.
* На сервере появляется второй рантайм-стек — больше памяти суммарно.
  Компенсируется лимитами в Compose.

## Путь назад

Протокол синка версионирован (`/api/v1`). Замена реализации сервера на Rust/axum
не требует изменений в клиенте, пока держится контракт из `@zapiski/core/sync`.
