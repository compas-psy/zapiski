# Тестирование

Тесты в этом репозитории — не «покрытие ради покрытия»: почти каждый файл
привязан к конкретному пункту приёмочного листа
[`../ACCEPTANCE.md`](../ACCEPTANCE.md) или к инварианту
[`../ARCHITECTURE.md`](../ARCHITECTURE.md) §3.

Раннер везде — **vitest**.

## Как запускать

```bash
pnpm test                              # всё
pnpm --filter @zapiski/core test
pnpm --filter @zapiski/core test:coverage
pnpm --filter @zapiski/editor test
pnpm --filter @zapiski/ui test
pnpm --filter @zapiski/app test
pnpm --filter @zapiski/server test

pnpm typecheck                         # tsc --noEmit по всем пакетам
pnpm lint:tokens                       # «ни одного hex вне токенов»
```

CI (`.github/workflows/deploy-zapiski.yml`, job `preflight`) выполняет
`typecheck` → `lint:tokens` → `test` → сборку PWA → валидацию
`docker-compose.yml` и vhost nginx. Шаги включаются сами, когда в воркспейсе
появляется соответствующий скрипт; `|| true` нет нигде — настоящая ошибка не
спрячется. Проверки инфобеза вынесены в отдельный workflow `security.yml`,
чтобы идти и на PR из форка, где секретов нет.

## Сколько чего

Замер `pnpm -r test` на версии 0.1.0:

| Пакет | Файлов | Тестов |
| --- | ---: | ---: |
| `packages/core` | 15 | 215 |
| `server` | 14 | 164 |
| `packages/editor` | 12 | 155 |
| `packages/ui` | 3 | 109 |
| `packages/app` | 7 | 52 |
| **Всего** | **51** | **695** |

`apps/*` продуктовых тестов не имеют и иметь не должны: в оболочках нет
продуктовой логики, а платформенные порты проверяются только на устройстве.
Единственное исключение — `pnpm --filter @zapiski/mobile test`: это
самопроверка патча `AndroidManifest.xml` (22 проверки + `xmllint`), которая
идёт без Android SDK и ловит поломку оверлея раньше сборки.

Покрытие ядра — **94.08 %** строк, 91.97 % функций, 83.29 % ветвей
(`pnpm --filter @zapiski/core test:coverage`, отчёт в
`packages/core/coverage/`). Требование ТЗ — >80 %. Перф-тесты из покрытия
исключены намеренно: инструментирование v8 утраивает время разбора заметки
1 МБ и меряло бы не тот код.

## «Злой синк»

Требование ТЗ §4.3 и §8, пункт A1 приёмочного листа:

> Параллельная правка одной заметки на 3 устройствах оффлайн → все сходятся к
> одному состоянию **без потерь**.

`packages/core/test/evil-sync.test.ts` поднимает три независимых vault'а
(`android`, `windows`, `web`) поверх `MemoryVaultStorage`, общий
`LocalFolderBackend` играет роль «облака», у каждого свой `SyncEngine` со своим
`deviceName`. Дальше — правки вразнобой и `sync()` в разном порядке.

Что именно проверяется:

1. **Сходимость.** После нескольких раундов все три устройства держат
   идентичный текст, и **все три правки в нём присутствуют**: правка Android,
   правка Windows и добавление из веба.
2. **Никаких маркеров конфликта.** В тексте нет `<<<<<<<` — экрана «выберите
   версию» в продукте не существует, и мусора в тексте тоже.
3. **Очередь переживает перезапуск** (`BEHAVIOR.md` §6): новый `SyncEngine`
   поверх того же хранилища видит незавершённые изменения.
4. **Оффлайн не ломает работу**: текст сохранён локально, статус — `offline`,
   текст сообщения дословно из реестра §11.
5. **Гибридный режим**: облачная версия главная, снапшот локальной уходит в
   историю версий.
6. **Зашифрованные не сливаются**: сохраняются обе версии, вторая — с суффиксом
   «(конфликт, устройство …)».
7. Отдельный блок про слияние текстов: CRDT сводит расходящиеся правки; diff3
   берёт правку одной стороны, когда вторая не менялась; объединяет
   непересекающиеся правки; **честно сообщает `ok: false`** о неразрешимом
   конфликте вместо того, чтобы писать маркеры в текст.

Матрица «Android × Windows × Web × (WebDAV, Я.Диск, локально)» из DoD пока
покрыта только по одной оси: бэкенд в тесте — `LocalFolderBackend`. WebDAV и
Яндекс.Диск проверяются вручную, потому что для них нужен настоящий сервер.

## Перф-бюджеты

Закреплены `ARCHITECTURE.md` §4 как автотесты, а не пожелания.

| Бюджет | Где | Состояние |
| --- | --- | --- |
| FTS <50 мс на корпусе 10 000 заметок | `packages/core/test/perf.test.ts` | ✅ три сценария: по слову, с операторами и фразой, по точной фразе; плюс backlinks на большом корпусе |
| Открытие заметки <150 мс (файл 1 МБ) | там же | ✅ |
| Обновление ссылок при переименовании — транзакционно | `packages/core/test/rename.test.ts` | ✅ |
| «Злой синк»: 3 устройства оффлайн → одно состояние | `packages/core/test/evil-sync.test.ts` | ✅ |
| Ввод <16 мс на кейстрок в заметке 1 МБ | `packages/editor/test/perf.test.ts` | ✅ |
| Открытие заметки 1 МБ в редакторе <150 мс | там же | ✅ |

Измерения берутся по медиане нескольких прогонов и печатаются в консоль — на
общем раннере абсолютные числа плавают, но регрессию в разы видно сразу.

**Абсолютные числа не переносите из этого файла в отчёты.** На нагруженной
машине один и тот же изолированный прогон даёт FTS по слову то 7 мс, то 47 мс, а
открытие заметки — то 39 мс, то 64 мс. Смысл имеет только соотношение с
бюджетом; для примера, один спокойный прогон здесь дал: FTS по слову 46.6 мс,
FTS с операторами 7.6 мс, FTS по точной фразе 33.1 мс, открытие заметки
1.03 МБ — 63.5 мс, кейстрок в редакторе — медиана 1.63 мс при p95 2.64 мс.

**Важно: перф-тесты нельзя оценивать по результату полного прогона.**
`pnpm -r test` запускает пакеты параллельно, и на загруженной машине бюджеты не
выдерживаются просто из-за конкуренции за процессор — измеряется не код.
Проверять надо изолированно:

```bash
pnpm --filter @zapiski/core exec vitest run test/perf.test.ts
pnpm --filter @zapiski/editor exec vitest run test/perf.test.ts
```

Порядок величин ядра на спокойной машине: FTS по слову — единицы миллисекунд,
FTS с операторами — около 5 мс, по точной фразе — около 20 мс, открытие
заметки 1 МБ — около 40 мс. Красный изолированный прогон — это уже регрессия.

Перф-тест редактора возможен без браузера потому, что
`buildLivePreview(state, ranges)` сделана чистой функцией: не требует
`EditorView` и не трогает DOM.

## Тесты сервера и Postgres

`server/test/globalSetup.ts` ищет базу в таком порядке:

1. `TEST_DATABASE_URL`, если задана;
2. локальные `initdb`/`pg_ctl` — поднимается одноразовый кластер во временном
   каталоге на свободном порту и гасится после прогона;
3. ничего не нашлось — тесты, которым нужна база, помечаются **пропущенными**, а
   те, что её не требуют (санитайзер, JWT, схема, контракт), идут как есть.

Используется настоящий Postgres, а не эмулятор: проверяются `FOR UPDATE`,
частичные индексы и `ON CONFLICT` — то, на чём держатся квота и одноразовость
magic-токена. Файлы идут последовательно (`fileParallelism: false`): тесты квоты
и лимитов иначе мешали бы друг другу через общий счётчик.

## Чего тестами не проверить

Зафиксировано честно в [`../ACCEPTANCE.md`](../ACCEPTANCE.md), повторено здесь,
чтобы не выдавать непроверенное за проверенное:

* сборка и запуск на **реальном Android-устройстве** — нет SDK/NDK локально;
* сборка **Windows-installer** — нет Windows-тулчейна локально;
* **реальное развёртывание на сервер** — значения секретов нечитаемы через API
  GitHub;
* регрессия ввода на **реальных клавиатурах** (Gboard, Яндекс.Клавиатура,
  SwiftKey) — QA-приоритет №1, но требует физических устройств;
* **контраст на OLED** — требует устройства.

Отдельно про пункт A3 приёмки: `packages/core/test/import.test.ts` есть и
проверяет все четыре источника, но **не на корпусе 1000+ заметок с
вложениями**, как требует DoD. Полная проверка ждёт реального Obsidian-vault.

Ещё две дыры, которые не закрываются тестами по построению:

* **Платформенные порты не покрыты вовсе.** Windows Hello, Android Keystore,
  WebAuthn-PRF, `FLAG_SECURE`, трей, виджеты, share-target, апдейтеры
  проверяются только на устройстве. Автотестов на них нет и быть не может.
* **Ни один клиентский артефакт не запускался.** Установщик Windows и APK ни
  разу не собраны; всё, что о них известно, — что код workflow'ов написан и что
  типы сходятся.
* **Матрица DoD «Android × Windows × Web × (WebDAV, Я.Диск, локально)»** не
  проверялась ни разу: из трёх бэкендов автотестами покрыт один
  (`LocalFolderBackend`), а Яндекс.Диск и облако КОМПАС в интерфейсе даже не
  подключаются.
