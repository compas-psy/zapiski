# Соглашения

Правила, которые в этом репозитории не обсуждаются в каждом PR заново.
Большинство из них — не вкусовщина, а прямое следствие ТЗ или
[`../ARCHITECTURE.md`](../ARCHITECTURE.md); нарушение части из них — блокирующий
дефект на приёмке.

## Язык

**Комментарии, сообщения об ошибках, названия тестов и коммиты — по-русски.**
Идентификаторы — по-английски (это код, а не текст).

Комментарий отвечает на вопрос «почему так», а не «что здесь написано».
Хороший образец — шапки файлов ядра: они объясняют, какое требование ТЗ файл
реализует и какое решение и почему принято.

```ts
// Плохо:
// увеличиваем счётчик
counter += 1;

// Хорошо:
// Замена символ-в-символ: длина документа не меняется, курсор и скролл
// остаются на месте, отмеченная задача никуда не переезжает (BEHAVIOR §2.3).
```

Ссылка на пункт спецификации в комментарии — норма, а не излишество: через
полгода она объяснит, почему нельзя «просто упростить».

## Приоритет документов

При расхождении:

```
docs/spec/BEHAVIOR.md
  > docs/spec/SCREENS.md
    > docs/spec/DESIGN_TOKENS.md
      > docs/spec/README.md (ТЗ)
        > docs/ARCHITECTURE.md
```

**Если поведение не описано ни в одном документе — реализующий обязан
спросить, а не решить самостоятельно.** Это дословное требование ТЗ.

`docs/spec/**`, `docs/ARCHITECTURE.md`, `docs/ACCEPTANCE.md` и `docs/adr/**` —
чужие документы. Их читают и на них ссылаются, но не редактируют без
согласования с владельцем.

## ADR

Стек в ТЗ §2.2 — **рекомендация**, отклонения разрешены явно, но **только с
обоснованием в ADR**.

Правило простое: **любое отклонение от рекомендованного стека или от буквы ТЗ
фиксируется отдельным ADR в `docs/adr/`, до того как код попадёт в `main`.**

Формат — как у существующих трёх:

1. Номер, заголовок, статус, дата, автор, **от чего именно отклоняемся**
   (с точной ссылкой на пункт).
2. **Контекст** — какая задача и какое требование перевешивает.
3. **Решение** — что именно делаем, с таблицей «требование ТЗ → чем закрыто».
4. **Последствия** — плюсы и, обязательно, минусы с указанием, чем они
   удерживаются под контролем.
5. **Путь назад** — как отменить решение, если оно окажется неверным.

Действующие: [ADR-0001](../adr/0001-yadro-na-typescript-vmesto-rust.md) (ядро на
TypeScript), [ADR-0002](../adr/0002-indeks-i-fts-bez-sqlite.md) (индекс без
SQLite), [ADR-0003](../adr/0003-backend-na-node-i-izolyaciya-na-cmpas-ru.md)
(бэкенд на Node и изоляция на cmpas.ru).

## Границы пакетов

**Публичный API пакета — только `src/index.ts`.** Глубокие импорты
(`@zapiski/core/src/internal/...`) запрещены — `ARCHITECTURE.md` §5.

Каждый пакет владеет своим каталогом. Не редактировать чужой: если нужен
экспорт — запросить его у владельца через интерфейс, а не дописать себе.

Направление зависимостей:

```
apps/*  →  packages/app  →  packages/{ui, editor, core}
```

Отдельно: **`packages/editor` не импортирует `@zapiski/core`.** Всё внешнее
приходит через `EditorRuntime`. Это не формальность — благодаря ей редактор
тестируется и показывается в витрине без vault'а, индекса и хранилища.

### Правило `apps/*`

В `apps/*` не должно быть **ни одного экрана, ни одной кнопки, ни одной строки
продуктовой логики**. Только точка входа, реализация платформенных портов и
платформенный манифест.

Экран, добавленный в `apps/web`, но не в `apps/mobile`, — это ровно тот дефект,
из-за которого провалился Android Obsidian. Такой код не принимается (пункт D1
приёмочного листа).

Практическое следствие, с которым вы столкнётесь: если оболочке «не хватает
способа что-то сделать» — не хватает **порта**, и добавлять нужно порт в
`AppHost` (`packages/app/src/contract.ts`) или в `PlatformCapabilities`
(`packages/core/src/contract.ts`), а не ветвление по платформе. Оболочка,
которой нечего предложить, честно возвращает `null` с комментарием, **почему** —
без комментария следующий разработчик примет ограничение платформы за
недоделку. Разбор всех таких случаев — [modules/platforms.md](modules/platforms.md).

## Серверные правила, добытые дорого

Каждое написано по следу поломки, которая уже случилась. Правило, которое
нигде не записано, теряется — так они и терялись.

### Имена сборок: правило СИМПАС, одно на три продукта

```
Имя файла:         simpas-<продукт>-<версия>.apk
Тег релиза:        <продукт>-v<версия>
Постоянная ссылка: /updates/latest/<продукт>.apk
```

`<продукт>` — ровно одно из `praktika`, `zapiski`, `momenty`. Здесь — `zapiski`;
версия берётся из `apps/mobile/src-tauri/tauri.conf.json` и на сегодня равна
`0.1.0`, то есть `simpas-zapiski-0.1.0.apk`, тег `zapiski-v0.1.0`, ссылка
`/updates/latest/zapiski.apk`.

Приставка `simpas` — по имени СИСТЕМЫ, объединяющей три продукта, а не по имени
одного из них: `kompas`/`compas` — это один продукт из трёх, и его имя на файлах
остальных закрепляет ту самую путаницу, из-за которой КОМПАС транслитерировался
тремя способами сразу (`kompas` в МОМЕНТАХ, `compas` в имени организации,
`cmpas` в домене).

Ни хеша коммита, ни номера прогона: имя человек видит у себя в загрузках, и
`-a3f9c21` ему ничего не сообщает — версии достаточно. Релиз соответствует
ВЕРСИИ, а не прогону сборки: пересобрали ту же версию — обновляется
существующий релиз и его файл, новый не создаётся. Иначе растёт лестница
`b19, b20, b23` при неизменном продукте.

**Правило касается имён артефактов, не инфраструктуры.** `applicationId`
(`ru.cmpas.zapiski`), ключ подписи, домен `cmpas.ru` и организация `compas-psy`
не переименовываются: смена `applicationId` означает для системы ДРУГОЕ
приложение — обновление поверх установленного перестанет работать, у человека
окажутся две иконки. То же и с ключом.

Правки сборки, подписи, разрешений и имён — исправление доставки, а не новая
версия продукта: `versionCode` и `versionName` при них не растут.

Держит `apps/mobile/scripts/android-release-gate.mjs names` — шаг сборки,
падающий на неверном имени или теге и называющий ожидаемое. Правило,
записанное только здесь, забывается; падающая сборка — нет.

### Номер миграции берётся в ветке по умолчанию

Файлы применяются `.sort()`, то есть по алфавиту, а `version` в
`schema_migrations` — это полное имя без `.sql`. Значит два файла с одним
номером раннер не считает конфликтом: применятся оба, а порядок между ними
решит хвост имени, не номер.

Один номер занимали дважды **трижды подряд** — всякий раз потому, что ветка
брала «следующий свободный» у себя, не зная про соседнюю. Поэтому: следующий
свободный номер смотрится в ветке по умолчанию, а не в своей.

Держится `server/test/migrations.numbering.test.ts`: дубль номера и дыра в
нумерации роняют прогон, в сообщении — какие именно файлы столкнулись.

Уже применённую миграцию переименовывать нельзя: раннер узнаёт её по имени и
по контрольной сумме — нужна новая.

### Пропуск тестов обязан быть громким

22 файла серверных тестов обёрнуты в `describe.skipIf(noDatabase())` —
маршруты, миграции, вход, вся аналитика. Базу поднимает `test/globalSetup.ts`
эфемерным кластером; если бинарей Postgres не нашлось, он печатал
`console.warn` и прогон продолжался **зелёным**.

Отказ выглядел неотличимо от успеха. В CI это худший из возможных исходов:
шаг «Тесты» показывает галочку, а проверено меньше половины сервера — и
именно на эту галочку смотрят перед выкладкой. Ни одна строка в логе не
говорила «половина не проверялась»: предупреждение тонуло среди тысячи строк
вывода, а итоговая сводка честно рапортовала о пройденных тестах, просто их
было вдвое меньше, чем кажется.

Вторая половина той же поломки — как именно искалась база. Каталоги
перечислялись жёстким списком версий (14, 15, 16). В день, когда раннер
переехал бы на 17, поиск перестал бы находить Postgres, и отказ выглядел бы
не как упавшая сборка, а как «тестов стало меньше», то есть никак.

Закрыто так: в CI ненайденная база — падение с внятной причиной, на машине
разработчика поведение прежнее (там Postgres может отсутствовать законно);
сознательный прогон без базы возможен только явной переменной
`ZAPISKI_ALLOW_NO_DATABASE=1`, которую нельзя выставить случайно. Версии
больше не перечисляются: вычитываются из `/usr/lib/postgresql`, новая
пробуется раньше старой. Держат `server/test/pg-discovery.test.ts` и сам
`globalSetup`.

Правило шире Postgres: **любое условие, которое отключает часть проверок,
обязано отличать «пропущено» от «пройдено» на уровне кода выхода.** Пропуск,
о котором знает только предупреждение в логе, — это зелёный свет, купленный
за молчание.

### Периодические задачи выполняются при старте, а не только по таймеру

Голый `setInterval` на длинный период — это задача, которая не выполнится
никогда, если процесс перезапускают чаще периода. Уборка с часовым интервалом
не проходила **ни разу**: каждая выкладка пересоздавала контейнер и обнуляла
отсчёт. Молча — ничего не падает и ничего не пишется в лог.

Поэтому у любой периодической задачи есть прогон вскоре после старта.
Не мгновенный: подъём сервера не должен ждать обход базы, — но на порядки
раньше периода. Образец — `server/src/services/sweep.ts`, держится
`server/test/sweep.startup.test.ts`.

Отсюда же второе: расписание живёт в отдельном модуле, а не в `index.ts`.
`index.ts` зовёт `main()` прямо при импорте, поэтому всё, что в нём объявлено,
тестом не проверяется в принципе.

### Файлы на сервер едут `rsync -e ssh`, а не `scp`

`scp`, начиная с OpenSSH 9.0, передаёт файлы **через подсистему SFTP**. На
нашем сервере она не отвечает, поэтому `scp` встаёт молча до потолка шага, а
`ssh`, `rsync -e ssh` и `ssh "cat > файл"` работают: они ходят обычным
exec-каналом.

Симптом обманчив ровно настолько, чтобы увести в сторону: интерактивный `ssh`
отвечает за секунды, `mkdir` на сервере проходит — сервер выглядит живым, и
поломку хочется списать на объём («большой файл не проходит, чёрная дыра
MTU»). Опровергается фактом, который лежит рядом и ничего не стоит: в те же
минуты, на тот же сервер, тем же ключом успешно ходит деплой веба. Он
передаёт больше и не падает — потому что ходит `rsync`.

Отсюда правило и способ его проверять: **прежде чем винить сеть или размер,
найдите соседа, который ходит туда же и работает, и сравните способ.**

```bash
# Плохо: встанет молча.
scp -i ~/.ssh/deploy_key файл "${USER}@${HOST}:${DIR}/"

# Хорошо: тот же ключ, тот же сервер, работающий транспорт.
timeout 300 rsync -a --partial -e "ssh -i ~/.ssh/deploy_key" файл "${USER}@${HOST}:${DIR}/"
```

`--partial` оставляет недокачанное — прерванная передача продолжается, а не
начинается заново. `-z` для APK и установщиков не нужен: они уже сжаты.

Держится `server/test/deploy.transport.test.ts` — он запрещает `scp` во всех
workflow разом.

### Потолок у шага заканчивает молчание, но не объясняет его

`timeout-minutes` у шага — не диагностика. Прогон 188 «Сборка Android»
простоял на выкладке пять минут, не напечатав ни строки, и был убит раннером.
Шаг звал четыре команды подряд; какая из них встала, из лога установить было
нельзя вовсе.

Поэтому: **потолок есть у каждой команды, а не только у шага**, и шаг
называет фазу вслух.

```bash
phase='подготовка ключа'
trap 'echo "::error::Выкладка встала на: ${phase}"' ERR

phase='передача APK'
timeout 300 scp -i ~/.ssh/deploy_key artifacts/*.apk "${USER}@${HOST}:${DIR}/"
```

Тогда падает команда, а не шаг, — и падает раньше потолка шага, то есть
успевает быть названной. Потолок шага остаётся последним рубежом.

Отдельно про ssh: `ConnectTimeout` **не покрывает разрешение имени**. Клиент
блокируется в `getaddrinfo`, и ни один из ssh-таймаутов (`ConnectTimeout`,
`ServerAliveInterval`, `ServerAliveCountMax`) к этому месту не относится. Это
и выглядит как «висит, ничего не печатая». Имя разрешается отдельной командой
с потолком, до всякого ssh.

Держится `server/test/deploy.ssh-timeouts.test.ts`.

### Через outputs job не ездит ничего, что содержит значение секрета

GitHub вычёркивает значения секретов из логов **подстрокой** и по тому же
правилу отказывается пропускать через `outputs` job любое значение, где такая
подстрока встретилась:

```
Skip output 'apk' since it may contain secret.
```

Отказ приходит не ошибкой, а **пустой строкой** — а пустая строка выглядит
как значение. У нас значение одного из секретов — само слово `zapiski`,
поэтому под правило попадает имя любого файла сборки.

Поэтому имена не передаются между job, а считаются в каждом заново — одним и
тем же расчётом (`apps/mobile/scripts/android-release-gate.mjs names --print`).
Два места, где имя написано буквами, разъезжаются молча; место, где оно
считается, — одно.

Держится `server/test/deploy.android-outputs.test.ts`.

## Стиль кода

TypeScript в строгом режиме, конфиг общий (`tsconfig.base.json`):
`strict`, `noUncheckedIndexedAccess`, `noImplicitOverride`, `isolatedModules`,
цель ES2022, модули ESNext.

* `noUncheckedIndexedAccess` включён — доступ по индексу даёт `T | undefined`.
  Отсюда `as` в местах разбора регулярок; это осознанная цена, а не небрежность.
* Импорты внутри пакета — с расширением `.js` (ESM + `moduleResolution:
  bundler`).
* Экспортируемые сущности снабжаются JSDoc с ссылкой на пункт спецификации.
* Никаких `any` в публичных сигнатурах.
* Ошибки, которые пользователь увидит, — только из каталога i18n.
* `catch {}` без комментария — повод для вопроса на ревью. Молчаливое
  проглатывание допустимо там, где это обосновано (повреждённый служебный файл:
  всё восстановимо из `.md`), и такое место комментируется.

## Чего мы не делаем никогда

Продуктовые красные линии (ТЗ §1, `ACCEPTANCE.md` §F) — не «пока не делаем», а
«не делаем»:

> базы данных и формулы · канбан · встроенный календарь-планировщик ·
> таск-менеджер с напоминаниями · сторонние плагины · геймификация ·
