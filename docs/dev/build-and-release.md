# Сборка и релиз

Как собираются веб, Windows и Android, какие workflow'ы за что отвечают, как
работает автообновление и какие секреты для этого нужны.

> **Честное состояние на 0.1.0.** Реально работает только конвейер сервера и
> статики: `deploy-zapiski.yml` + `provision-zapiski.yml`. **Клиентских сборок в
> репозитории нет вообще** — нет ни `apps/web`, ни `apps/desktop`, ни
> `apps/mobile`, ни workflow'ов сборки Windows/Android, ни конфигов Tauri.
> Разделы про десктоп и Android ниже описывают, что должно быть сделано, и
> явно помечены как запланированные.

---

## Веб (PWA)

**Планируемая схема.** `apps/web` — тонкая оболочка на Vite: монтирует `<App/>`
из `packages/app` и даёт реализацию `VaultStorage` поверх File System Access API
(Chromium) или OPFS (остальные браузеры). Продуктовой логики в оболочке нет ни
строки — правило [`../ARCHITECTURE.md`](../ARCHITECTURE.md) §1.

Сборка из корня:

```bash
pnpm build              # packages/** + @zapiski/web
pnpm --filter "@zapiski/web..." build   # именно так это делает CI: пакет со своими зависимостями по графу
```

Результат — `apps/web/dist`, который job `preflight` кладёт артефактом
`zapiski-web-dist`, а job `deploy` выкладывает rsync'ом в
`/var/www/zapiski.cmpas.ru`.

> ⏳ Пакета `@zapiski/web` нет, поэтому `pnpm build` и `pnpm dev` в корне сейчас
> падают, а шаги «Сборка PWA» и «Выложить статику PWA» в CI сами себя
> пропускают: workflow определяет состав воркспейса скриптом и включает шаги по
> факту наличия пакета. Это сделано намеренно — пайплайн готов раньше кода.

Что оболочка обязана сделать, кроме монтирования:

* вставить инлайном `themeInitScript` из `@zapiski/ui` в `<head>` — иначе первый
  кадр мигнёт светлым;
* отдать `manifest.webmanifest` и service worker (в vhost для них уже прописан
  `no-cache`);
* реализовать `PdfRenderer` через печать скрытого iframe;
* реализовать `BiometricProvider` через WebAuthn-PRF, если браузер умеет, иначе
  вернуть `null` — и UI **скроет** тумблер биометрии, а не покажет его
  выключенным.

## Windows (Tauri 2)

> ⏳ **Не реализовано.** Ни `apps/desktop`, ни workflow сборки, ни конфига Tauri
> в репозитории нет.

Что запланировано (ТЗ §2.2, ADR-0001):

* Tauri 2, сборка на раннере `windows-latest` (локально Windows-тулчейна нет —
  зафиксировано в [`../ACCEPTANCE.md`](../ACCEPTANCE.md));
* `VaultStorage` поверх `@tauri-apps/plugin-fs`;
* глобальный хоткей быстрой заметки (по умолчанию `Ctrl+Alt+N`), автозапуск в
  трей, ассоциация `.md`;
* `UpdaterProvider` на встроенном апдейтере Tauri;
* цель по размеру: installer < 25 МБ (ТЗ §6).

Артефакты релиза (`.msi`, `.exe`, `.sig`) кладутся в
`/var/www/zapiski.cmpas.ru/updates/`. Обычный деплой веба их не сносит: rsync
исключает `updates/`.

## Android (Tauri 2 Mobile)

> ⏳ **Не реализовано.** Ни `apps/mobile`, ни workflow, ни манифеста.

Что запланировано:

* сборка на раннере GitHub Actions (Android SDK/NDK локально нет);
* тот же `VaultStorage` поверх `@tauri-apps/plugin-fs`;
* share-target (текст/ссылка/изображение), виджеты (быстрая заметка 1×1,
  последние 2×2, закреплённая 2×2), Quick Settings tile, деликатная хэптика,
  `FLAG_SECURE`;
* цель по размеру: APK < 30 МБ (ТЗ §6);
* **риск-зона №1** из ТЗ §2.2: качество WebView-редактора на Android (IME,
  Gboard / Яндекс.Клавиатура / SwiftKey, автозамена, свайп-ввод, кириллица).
  Защита в коде уже написана — см.
  [modules/editor.md](modules/editor.md#проблема-ime), но подтверждать её
  придётся на реальных устройствах.

**Про подпись Android — важное.** Алиас и keystore **нельзя менять после первой
публикации**: обновление с другой подписью не встанет поверх установленного
приложения, пользователю придётся удалять и ставить заново, теряя данные.

## Workflow'ы

В репозитории их два, оба описаны по-русски прямо в файлах.

### `provision-zapiski.yml` — «Провижн zapiski.cmpas.ru (nginx + TLS)»

Запускается вручную и при изменениях в `deploy/**` в ветке `main`.
**Выполняется один раз перед первым деплоем.**

1. Проверяет синтаксис vhost локально, в контейнере `nginx -t` — **до** отправки
   на сервер.
2. Создаёт `/var/www/zapiski.cmpas.ru` и `.../updates`.
3. Кладёт vhost в `sites-available`, делает симлинк, `nginx -t`, и
   `systemctl reload nginx` **только при успехе**; при провале снимает симлинк.
4. Выпускает сертификат `certbot --nginx -d zapiski.cmpas.ru` — **строго один
   домен**, только если сертификата ещё нет.
5. Клонирует репозиторий в `/var/www/zapiski`.

### `deploy-zapiski.yml` — «Деплой zapiski.cmpas.ru»

Автоматически на каждый push в `main` (кроме изменений только в `docs/**` и
`*.md`), а также на pull request — но тогда выполняется только `preflight`.

**Job `preflight`** (раннер `ubuntu-latest`, Node 22, pnpm):

1. `pnpm install` (`--frozen-lockfile`, если есть lock-файл);
2. определяет состав воркспейса скриптом и включает следующие шаги по факту;
3. `pnpm -r typecheck`;
4. `pnpm run lint:tokens` — инвариант «ни одного hex вне токенов»;
5. `pnpm -r test`;
6. сборка PWA → артефакт `zapiski-web-dist`;
7. `docker compose config --quiet` — битый YAML обнаружится здесь, а не на проде
   в момент `up -d`;
8. `nginx -t` для vhost в контейнере;
9. `bash -n` для скрипта удалённого деплоя.

**Job `deploy`** (только push в `main`):

1. забирает артефакт статики;
2. проверяет, что провижн уже выполнен (есть docroot и рабочая копия);
3. rsync статики в docroot с `--delete`, исключая `updates/` и `.well-known/`;
4. по ssh: `git fetch && git reset --hard origin/main` в `/var/www/zapiski`,
   затем `bash deploy/deploy-production-remote.sh`;
5. при провале скачивает `/tmp/zapiski-deploy.log` и прикладывает артефактом
   `zapiski-deploy-<sha>`.

Секреты уезжают на сервер **одним base64-блобом**, а не отдельными аргументами:
апостроф или `;` внутри значения иначе исполнился бы как код, а пустой аргумент
схлопнулся бы при склейке ssh-команды и сдвинул позиции.

Оба job'а, которые трогают сервер, делят группу concurrency `zapiski-server` с
`cancel-in-progress: false` — начатую выкладку на прод не обрывают, и провижн с
деплоем никогда не идут одновременно.

### Изоляция от КОМПАС.Дневника

Сервер `cmpas.ru` — действующий продакшен Дневника. Главный риск этого этапа —
не выбор технологии, а **уронить работающий Дневник**, поэтому:

* nginx в обычном деплое **не упоминается вообще**;
* rsync пишет строго в `/var/www/zapiski.cmpas.ru`; каталог `/var/www/cmpas.ru`
  не встречается ни в одном файле деплоя;
* `deploy-production-remote.sh` начинается с проверки «а туда ли меня
  запустили», и каждая изменяющая docker-команда явно привязана к
  compose-проекту `zapiski`;
* контейнер Дневника упоминается ровно один раз, в самом конце, и только в
  `docker inspect` — чтобы записать в лог, что он как работал, так и работает.

Полные правила — [ADR-0003](../adr/0003-backend-na-node-i-izolyaciya-na-cmpas-ru.md)
и [`../../deploy/SETUP.md`](../../deploy/SETUP.md).

## Автообновление

**Схема.** Клиент (Tauri updater) ходит на
`https://zapiski.cmpas.ru/api/v1/updates/{{target}}/{{current_version}}`.
Сервер читает JSON-манифест из тома (`UPDATES_MANIFEST_PATH`) и отвечает:

* `200` + манифест — если в манифесте версия новее текущей;
* **`204` без тела** — если новее нет. Это единственный способ сказать Tauri
  «обновления нет»; `200` с той же версией заставил бы клиента качать то, что
  уже установлено.

Манифест:

```jsonc
{
  "version": "0.2.0",
  "notes": "Что изменилось",
  "pub_date": "2026-09-01T10:00:00Z",
  "platforms": {
    "windows-x86_64": { "signature": "<подпись Tauri>", "url": "https://zapiski.cmpas.ru/updates/zapiski_0.2.0_x64.msi" },
    "android-universal": { "signature": "", "url": "https://zapiski.cmpas.ru/updates/zapiski-0.2.0.apk" }
  }
}
```

Для Android подписи Tauri нет — обновление ставит сам пользователь, поэтому
`signature` пустая, а nginx отдаёт `.apk` с
`Content-Type: application/vnd.android.package-archive` (без него установщик
пакета не запустится, браузер просто покажет файл).

Файлы релиза кладутся в `/var/www/zapiski.cmpas.ru/updates/`. Кэширование в
vhost: `latest.json` — `no-cache` (иначе клиент неделю не узнает о релизе),
бинарники — час. `try_files … =404` принципиален: апдейтер должен получить
честный 404, а не HTML SPA-фолбэка.

> ⏳ **Конвейера, который наполняет `updates/`, нет.** Нет workflow сборки
> Windows и Android, нет шага подписи, нет шага выкладки манифеста. Пока в томе
> нет файла — фид честно отвечает `204`, и это корректное поведение «релизов
> ещё не было», а не поломка.

## Секреты

Кладутся в **Settings → Secrets and variables → Actions** репозитория.

### Обязательные для деплоя

| Секрет | Что это |
| --- | --- |
| `SERVER_HOST` | Адрес сервера |
| `SERVER_USER` | Пользователь SSH (имеет root: workflow пишет в `/etc/nginx` и делает `systemctl`) |
| `SSH_PRIVATE_KEY` | Приватный ключ целиком, вместе со строками `-----BEGIN…`/`-----END…` |

Значения секретов **нельзя прочитать ни через API, ни через UI, ни агентом** —
GitHub отдаёт их только раннеру во время исполнения. Это не ограничение
инструмента, а механизм безопасности: утёкший доступ к репозиторию не означает
утёкший доступ к серверу.

### По мере готовности функций

| Секрет | Для чего | Когда |
| --- | --- | --- |
| `YANDEX_CLIENT_ID` / `YANDEX_CLIENT_SECRET` | Яндекс ID (OAuth) — основной вход | Вместе с аккаунтами |
| `TAURI_SIGNING_PRIVATE_KEY` / `..._PASSWORD` | Подпись автообновлений Tauri; без неё апдейтер отклонит пакет | Первый релиз desktop |
| `ANDROID_KEYSTORE_BASE64` | Keystore подписи APK в base64 | Первый релиз Android |
| `ANDROID_KEYSTORE_PASSWORD` / `ANDROID_KEY_ALIAS` / `ANDROID_KEY_PASSWORD` | Там же | Там же |

Секреты, которые живут **только на сервере**, в `/var/www/zapiski/deploy/.env`
(в git его нет): пароль БД и `AUTH_SECRET` — генерируются скриптом деплоя при
первом запуске; `YOOKASSA_*`, `GOOGLE_PLAY_*` — дописываются руками. Образец —
[`../../deploy/.env.example`](../../deploy/.env.example).

Один раз руками, вне автоматики (подробно — в
[`../../deploy/SETUP.md`](../../deploy/SETUP.md)): A-запись `zapiski` в DNS,
три секрета доступа к серверу, deploy key для клонирования приватного
репозитория на сервер, Redirect URI в консоли Яндекс ID.

## Версионирование

Все пакеты сейчас на `0.1.0`. Версия продукта ведётся в
[`../product/changelog.md`](../product/changelog.md). Протокол облака
версионирован отдельно префиксом `/api/v1`: замена реализации сервера не
потребует изменений в клиенте, пока держится контракт.
