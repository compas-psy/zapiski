# SEC-001 — Zero-knowledge синхронизация: архитектурный проект

**Статус: проектный документ. Кода нет — ни строки.** Задача этого документа
— решить конструкцию, а не реализовать её. Реализация — отдельная работа,
отдельная приёмка, отдельный прогон `security.zero-knowledge.test.ts` и
аналогов.

**Не решение, а временная мера.** Скрытие пункта «Облако Записок» из
интерфейса до готовности этого проекта — допустимый **kill-switch на время
релиза**, не более того. Финальным ответом на SEC-001 «просто спрятать Cloud»
не является: рано или поздно облако нужно включить обратно, и включать его
обязано уже с настоящим шифрованием, а не с тем же дефектом под кнопкой,
которую снова нашли. Kill-switch реализован: `CLOUD_SYNC_ENABLED = false`
(`packages/core/src/cloud-sync.ts`), проверено тестом
(`packages/app/test/cloud-kill-switch.test.tsx`).

Связанные документы: `docs/dev/security/AUDIT.md` (находка SEC-001, полное
доказательство), `docs/dev/security/THREAT-MODEL.md` §2.2 (актёр
«скомпрометированный сервер синка», куда войдёт результат этой работы),
`docs/ARCHITECTURE.md` §3 (инвариант 3 — «zero-knowledge»).

## Ревизия closure-pass — что изменилось в этой редакции

Первая версия документа (в истории git — коммит, добавивший этот файл)
называла конструкцию «в целом решённой» и оставляла нонс-схему и вывод
ключей как «деталь для реализации». Заказчик по итогам P1-аудита потребовал
**hard security review** до перехода к коду — шесть конкретных вопросов,
не проходной формальности. Эта редакция отвечает на каждый предметно, меняя
конструкцию там, где первая версия была недостаточно строгой:

1. **Иерархия ключей (§2).** Было: один синк-ключ, используемый напрямую
   везде. Стало: SMK (sync master key) → HKDF с доменным разделением →
   отдельные подключи для содержимого/блобов, CRDT, версий, манифеста и
   обёртки при ротации — минимум, который требовал заказчик, плюс
   обоснование каждого домена.
2. **Стратегия нонса AES-GCM (§8).** Было: «монотонный счётчик, замешанный с
   `device_id`» — заказчик справедливо отклонил это как недоказанную схему.
   Стало: формальное обоснование, почему доменное разделение ключей (пункт 1)
   делает СЛУЧАЙНЫЙ 96-битный нонс безопасным по границе NIST SP 800-38D без
   какого-либо состояния устройства — и почему это одновременно и проще, и
   строже счётчика.
3. **Код восстановления (§6).** Было: «формат — вопрос дизайна, не
   инженерии». Стало: инженерия отдельно фиксирует минимум энтропии,
   источник случайности, контрольную сумму — формат представления остаётся
   дизайн-решением, но НАД зафиксированным инженерным минимумом, а не вместо
   него.
4. **Оффлайн-атака на пароль восстановления (новый §6.1).** Было: не
   называлось явно. Стало: явная модель угрозы «скомпрометированный сервер
   получает `wrapped_sync_key` + соль → офлайн-подбор пароля восстановления
   без троттлинга», конкретные параметры Argon2id и требование к бенчмаркам
   по платформам, запрет тихого понижения параметров.
5. **Защищённое локальное хранилище ключа (новый §3.1).** Было: «тот же
   платформенный порт, что и пароль vault'а» — без честной оговорки про Web.
   Стало: по каждой платформе отдельно, включая прямое признание, что Web/PWA
   не имеет аппаратного эквивалента Keychain/Keystore/DPAPI.
6. **Миграция plaintext → ciphertext (§10).** Было: подробно про порядок
   операций, но не про ПОЛНЫЙ список мест хранения. Стало: явный чек-лист
   каждого места (блобы, версии, CRDT, надгробия, файловая система сервера,
   Postgres, временные файлы, логи, очереди, бэкапы) — и честное признание,
   что резервных копий на сервере сегодня нет вовсе, а не выдуманная
   политика хранения задним числом.

Реализация по-прежнему не начата — эта ревизия и есть тот самый обязательный
шаг «сначала review, потом design, потом уже код», который заказчик описал.

## 0. Что уже есть и на что эта работа опирается

Прежде чем проектировать новое, стоит назвать то, что уже построено и
работает — проект использует это как готовый фундамент, а не изобретает
шифрование заново.

* **`packages/core/src/crypto/provider.ts`** — `WebCryptoProvider`: Argon2id
  (RFC 9106, набор 2) → HKDF-иерархия master → per-note ключ → AES-256-GCM с
  AAD на заголовке контейнера. Параметры и опасности задокументированы в коде
  и в ADR-0001. Это ровно тот криптографический набор, который нужен и здесь
  — переиспользуется целиком, без нового примитива.
* **`packages/app/src/state/store.ts`** — уже есть «проверочный блоб» без
  расшифровки содержимого (`openCheck`), уже есть троттлинг неверных попыток
  (`unlockDelayMs` — 0 → 30 с → 5 мин), уже есть платформенный порт
  `biometrics.enroll/unlock/remove`, которым материал ключа кэшируется в
  Keychain / Keystore / DPAPI. Всё это — готовые кирпичи для потока онбординга
  устройства ниже, не новые.
* **`packages/core/src/sync/engine.ts`** — уже есть ветка для случая, когда
  слияние текста невозможно: `isEncryptedPath(path)` (строка 762) не пытается
  сливать зашифрованный файл текстом, а сохраняет обе версии рядом
  (BEHAVIOR §5.4). Это ГОТОВАЯ модель поведения для «конфликт над
  шифротекстом» — ниже она не изобретается заново, а становится общим
  правилом.
* **`server/migrations/0002_vault.sql`** — таблица `crdt_updates` уже имеет
  колонку `ciphertext bytea` с комментарием «клиент шифрует апдейт перед
  отправкой» — это НЕ соответствует действительности сегодня (шифрования нет
  нигде в `sync/**`, доказано в AUDIT.md), но схема уже спроектирована под
  него. Часть работы дешевле, чем кажется: место для шифротекста уже вырыто,
  просто в него пока кладут открытый текст.
* **`blobs` (та же миграция)** — контентно-адресуемое хранилище на диске
  (`BlobStore`, ключ — SHA-256 шифротекста, имена в томе не повторяют имена
  vault'а). Но в Postgres у той же таблицы есть открытая колонка `path text`
  — «путь внутри vault'а», с комментарием «это пользовательские данные». Она
  и есть главный источник утечки метаданных (см. §7).

## 1. Клиентская граница шифрования

Граница — **не там же, где сегодня локальное шифрование по паролю**, и это
осознанное решение, а не совпадение.

Сегодня шифрование заметки (`crypto/notes.ts`, `.md` → `.md.enc`) —
добровольное действие человека над ОТДЕЛЬНОЙ заметкой: он ставит пароль,
заметка лежит на диске зашифрованной, ключ выводится из пароля. Это решает
угрозу «вор устройства» (THREAT-MODEL §2.3), но не обязано быть включено —
ТЗ §3.3 прямо называет его опциональным.

Новая граница — **на входе/выходе `SyncBackend`**, а не на уровне отдельной
заметки:

```
                          локально, всегда plaintext
                          (invariant #1: file over app)
┌──────────────┐   .md / .md.enc   ┌──────────────┐
│  диск, vault  │ ─────────────────▶│  SyncEngine  │
└──────────────┘                    │   (как есть, │
                                     │  без правок) │
                                     └──────┬───────┘
                                            │ plaintext-байты
                                            │ (или байты .md.enc,
                                            │  если человек сам
                                            │  зашифровал заметку)
                                     ┌──────▼────────────────┐
                                     │ ZapiskiCloudBackend    │
                                     │  .put()/.get()         │ ← ГРАНИЦА
                                     │  оборачивает/снимает    │
                                     │  envelope синк-ключом  │
                                     └──────┬─────────────────┘
                                            │ ciphertext (AES-256-GCM,
                                            │ синк-ключ, никогда не
                                            │ синхронизируемый как есть)
                                     ┌──────▼───────┐
                                     │    сервер    │
                                     └──────────────┘
```

Почему граница именно здесь, а не выше (в `SyncEngine`) и не ниже (в каждом
`SyncBackend` отдельно):

* **`SyncEngine.merge()` (diff3, CRDT three-way merge) не меняется вовсе.**
  Слияние текста продолжает работать с открытым текстом — на устройстве, как
  и сегодня. Не нужно «уметь сливать шифротекст» (это в принципе
  бессмысленно криптографически) — сервер как не умел интерпретировать
  содержимое, так и не умеет, а клиент сливает то же, что сливал всегда.
* **Граница — по одному классу (`ZapiskiCloudBackend`), а не размазана.**
  `WebdavBackend`/`YandexDiskBackend` (`sync/webdav.ts`, `sync/yandex.ts`) —
  это СОБСТВЕННОЕ хранилище человека, которое он сознательно подключил и уже
  доверяет ему как оператору (тот же класс доверия, что «свой NAS» или «свой
  Google Диск»). Обещание zero-knowledge в ТЗ и в письме входа относится к
  КОМПАС как оператору `zapiski.cmpas.ru`, а не к произвольному чужому
  хранилищу — так же прицельно, как этот же класс актёра уже описан в
  THREAT-MODEL §2.2 («Сюда же попадают WebDAV-провайдер и Яндекс.Диск, когда
  синк идёт через них» — то есть модель уже сегодня трактует их как
  РАЗНОВИДНОСТЬ того же актёра. Открытый вопрос §16.3 ниже — стоит ли и туда
  тоже включать обязательное шифрование; граница класса это позволяет сделать
  позже без переписывания).
* **Локальное шифрование по паролю (§3.3) и синк-шифрование становятся
  ортогональными**, а не одним и тем же переключателем: человек, который
  никогда не ставил пароль на заметку, получает защищённый транспорт и
  хранение на сервере автоматически, без единого нового вопроса в UI. Человек,
  который поставил пароль на конкретную заметку, продолжает получать то же
  самое — плюс синк-шифрование оборачивает уже зашифрованные байты SNAP
  ещё раз (двойное шифрование безвредно, дешёво, и не требует различать
  два случая в `ZapiskiCloudBackend`).

## 2. Иерархия ключей и жизненный цикл

### 2.1. Почему не один ключ на всё

Первая версия этого документа предлагала один синк-ключ, используемый
НАПРЯМУЮ на границе `ZapiskiCloudBackend.put/get` для содержимого, CRDT-
апдейтов и версий разом. Closure-pass review отклонил это: один ключ на
всё — это (а) отсутствие доменного разделения (компрометация ключа в одном
контексте компрометирует все остальные без исключения), (б) общий, не
разделённый бюджет нонсов AES-GCM на ОЧЕНЬ разных по частоте потоках
(CRDT-апдейты — на каждое автосохранение, манифест — раз в изменение
дерева папок), что и вынудило первую версию искать спасение в стойком к
ошибкам, но недоказанном счётчике (см. §8, было отклонено). Правильный
инструмент здесь уже есть в кодовой базе и один раз уже применён:

> **Терминология.** «Синк-ключ» — термин первой версии документа, дальше по
> тексту (§4, §5, §9, §11, §13, §15, §17) он используется как неформальный
> синоним **SMK** — верхнего ключа иерархии этого раздела, из которого HKDF
> выводит доменные подключи (§2.2). Там, где текст говорит именно про
> доменный подключ (`K_content`, `K_crdt`, `K_versions`, `K_manifest`,
> `K_wrap`), он называет его по имени явно — неоднозначности это не создаёт,
> поскольку граница шифрования (§1) как использовала «ключ синка» одним
> понятием, так и продолжает: разница только в том, ЧЕМ именно он
> реализован внутри.
`WebCryptoProvider.deriveNoteKey` — HKDF от мастер-ключа с доменной строкой
в `info`. Тот же приём, применённый на уровне синка, решает обе проблемы
разом и бесплатно.

### 2.2. Дерево ключей

```
                       crypto.getRandomValues(32)
                                  │
                                  ▼
                    ┌──────────────────────────┐
                    │  SMK — sync master key    │  256 бит, никогда не
                    │  (не выводится из пароля) │  покидает устройство
                    └─────────────┬─────────────┘  в открытом виде
                                  │ HKDF-SHA256, salt = соль аккаунта,
                                  │ info = доменная строка ниже
        ┌───────────┬────────────┼────────────┬───────────────┐
        ▼           ▼            ▼            ▼               ▼
  K_content    K_crdt       K_versions    K_manifest        K_wrap
  (per-note)   (per-note)   (per-note)    (один на          (один на
                                           аккаунт)          аккаунт)
```

Пять доменов — минимум, который потребовал заказчик, каждый с отдельным
обоснованием:

* **`zapiski/sync/v1/content/<note_id>`** → `K_content` — шифрует байты
  файла заметки (`.md`/`.md.enc`, уже возможно дважды зашифрованные, если
  человек сам поставил пароль на заметку — §3.3), которые уходят через
  `ZapiskiCloudBackend.put()` в `blobs`.
* **`zapiski/sync/v1/crdt/<note_id>`** → `K_crdt` — шифрует
  `crdt_updates.ciphertext`. Самый частый поток (каждое автосохранение), и
  именно поэтому он получает СОБСТВЕННЫЙ ключ, а не делит бюджет нонсов ни с
  чем ещё (см. §8).
* **`zapiski/sync/v1/versions/<note_id>`** → `K_versions` — шифрует
  `versions.storage_key` (тот же `BlobStore`, что и `content`, но ключ
  СВОЙ: история версий и текущее содержимое — разные объекты доступа,
  разная частота записи, компрометация одного не обязана раскрывать другой).
* **`zapiski/sync/v1/manifest`** — БЕЗ `note_id`: манифест vault'а (дерево
  папок, §7) — один объект на аккаунт, поэтому один ключ `K_manifest`, а не
  дерево по объектам.
* **`zapiski/sync/v1/wrap`** — БЕЗ `note_id`: `K_wrap` используется РОВНО
  для одного действия — обернуть НОВЫЙ SMK при ротации (§11) для каждого уже
  доверенного устройства через его СТАРЫЙ, ещё живой в памяти SMK, чтобы не
  требовать повторного ввода пароля восстановления на каждом устройстве при
  штатной ротации. `K_wrap` НИКОГДА не используется, чтобы обернуть сам SMK,
  из которого выведен, — это было бы бессмысленно криптографически
  (обёртка производной от секрета не защищает сам секрет от того, кто уже
  получил производную).

`<note_id>` в `info` — то же самое доменное разделение, что уже применяет
`deriveNoteKey` с `keyId` (`crypto/provider.ts:111`), только на уровень выше:
каждая заметка получает СВОЙ `K_content`/`K_crdt`/`K_versions`, выведенные из
ОДНОГО и того же SMK на каждом устройстве аккаунта независимо — устройству
для этого не нужно ничего, кроме уже имеющегося SMK и `note_id`, который оно
и так знает. Побочный эффект, важный для §8: у КАЖДОЙ заметки — свой,
маленький бюджет нонсов, а не общий на весь аккаунт.

Соль HKDF — публичная соль аккаунта (та же, что защищает `wrapped_sync_key`,
§3), а не отдельная для каждого домена: HKDF гарантирует криптографическую
независимость производных ключей по РАЗНЫМ `info`, разделяя соль незачем.

### 2.3. Жизненный цикл SMK

Состояния:

1. **Не существует** — аккаунт никогда не включал Облако Записок. Ничего не
   меняется относительно сегодняшнего дня.
2. **Создан** — первое включение синка на ПЕРВОМ устройстве аккаунта:
   генерируется случайный SMK, тут же оборачивается ключом восстановления
   (§3) и кэшируется локально через `biometrics.enroll`. Публично на сервер
   уходит только обёрнутый (зашифрованный) блоб — сам SMK во время всего
   жизненного цикла НИКОГДА не покидает устройство в незашифрованном виде.
3. **Действующий** — на каждой операции `ZapiskiCloudBackend.put/get`
   (§1) выводится нужный доменный подключ (§2.2) НА ЛЕТУ, HKDF без
   Argon2id — мгновенно, тот же принцип, что уже даёт `deriveNoteKey`. Сам
   SMK живёт в памяти процесса и в платформенном защищённом хранилище (§3.1)
   — новый ключ ID (например, `'sync'` рядом с существующим `'vault'`), а не
   новый механизм хранения.
4. **Ротация** — по требованию человека (см. §11, отзыв устройства) или по
   решению владельца продукта на будущее (регулярная ротация не входит в
   это предложение как обязательная — только по требованию). Ротация = новый
   случайный SMK + полный перешифровальный проход (тот же механизм, что
   миграция, §10, — с новыми доменными подключами, выведенными из нового
   SMK) + новая обёртка для ключа восстановления + обёртка `K_wrap`-ом для
   уже доверенных устройств (§2.2).
5. **Утрачен безвозвратно** — обе обёртки (пароль восстановления и код
   восстановления, §6) забыты одновременно. Локальные копии на уже
   подключённых устройствах остаются полностью читаемыми (invariant #2,
   local-first, никуда не делся) — утрачивается только возможность
   подключить НОВОЕ устройство или восстановить синк после переустановки.
   Это должно быть сказано человеку прямым текстом при установке пароля
   восстановления, а не подразумеваться.

## 3. Вывод и хранение ключей

Переиспользуется существующий примитив `deriveMasterMaterial`/`importMaster`
(`crypto/provider.ts`) один в один — просто с ДРУГИМ паролем и ДРУГИМ
назначением результата:

* **Пароль восстановления** (отдельный от пароля любой конкретной заметки —
  явно так и называется в UI, чтобы не путать с §3.3) → Argon2id (параметры —
  §6.1, НЕ автоматически те же, что у пароля vault'а: разные платформенные
  бюджеты времени, см. ниже) → ключ обёртки.
* Ключ обёртки шифрует (AES-GCM) SMK → `wrapped_sync_key`. Соль Argon2id —
  публичный параметр, живёт на сервере открытым текстом (как сегодня живёт
  соль vault'а в `.zapiski/meta/crypto.json` — тот же класс данных, тот же
  прецедент).
* Проверка правильности пароля восстановления — тем же приёмом, что уже
  есть в `store.ts` (`openCheck`: короткий проверочный блоб, а не попытка
  расшифровать реальные данные) — переиспользуется буквально, только на
  уровне аккаунта, а не vault'а.
* Неверный пароль восстановления — тот же `unlockDelayMs` (0 → 30 с → 5 мин),
  тот же прецедент, что уже защищает пароль vault'а от подбора. Это защищает
  только ОНЛАЙН-подбор (через сервер) — офлайн-подбор после компрометации
  сервера троттлинг не видит вовсе, см. §6.1.
* После успешного разворачивания SMK кэшируется на устройстве через
  платформенный порт `biometrics.enroll(ключ_id, материал)` — новый
  `ключ_id` (например, `'sync'` рядом с существующим `'vault'`). На каких
  платформах это действительно защищённое хранилище, а на каких —
  честно нет, см. §3.1.

### 3.1. Защищённое локальное хранилище SMK — по платформам честно

Первая версия документа говорила «тот же платформенный порт, что уже хранит
материал пароля vault'а» и на этом останавливалась — будто гарантия одна и
та же везде. Это неверно, и hard security review требует сказать так по
каждой платформе отдельно:

* **Android (Keystore).** Материал ключа физически не покидает
  StrongBox/TEE на устройствах, где он есть; на более старых — программная
  реализация Keystore, слабее, но всё ещё отдельная от процесса приложения.
  Реальная гарантия, соответствует уже принятому в продукте уровню доверия.
* **macOS (Keychain).** Тот же уровень: материал в Keychain, доступ через
  ACL процесса, при включённом Touch ID — дополнительный биометрический
  барьер. Реальная гарантия.
* **Windows (DPAPI).** Шифрование привязано к учётной записи Windows и
  машине; это защита от «другой пользователь этой машины» и «файл
  скопировали на другую машину», НЕ защита от вредоносного кода,
  исполняющегося под той же учётной записью, — это ограничение уже
  зафиксировано для пароля vault'а (тот же класс, ADR-0001, «Минусы»), здесь
  не появляется нового риска, только тот же самый.
* **Web/PWA — здесь честности не хватало.** Браузер не предоставляет
  аппаратного эквивалента Keychain/Keystore/DPAPI. Реалистичные варианты
  веба:
  * `IndexedDB` — материал ключа лежит в базе процесса рендерера, читаемой
    ЛЮБЫМ JavaScript-кодом с тем же origin (в т.ч. через XSS, если такая
    уязвимость когда-либо появится) и любым расширением браузера с
    разрешением на этот origin. Origin-изоляция — реальная, но не
    hardware-backed граница, какую даёт Keystore/Keychain.
  * WebCrypto `CryptoKey` с `extractable: false` (уже используется для
    master-ключа vault'а, `provider.ts:88`) НЕ решает эту проблему для SMK:
    непригодный для извлечения ключ всё ещё используется тем же
    JS-контекстом, который скомпрометирован при XSS, — непроницаемость
    ключа для ЧТЕНИЯ не мешает вредоносному коду в ТОМ ЖЕ origin им
    ПОЛЬЗОВАТЬСЯ (расшифровывать что угодно, пока код исполняется).
  * WebAuthn/`PRF`-расширение (там, где браузер его поддерживает) даёт
    ключевой материал, привязанный к аппаратному security key/платформенному
    аутентификатору — ближе всего к настоящей аппаратной защите в вебе, но
    доступность неравномерна (не все браузеры/устройства) и требует
    отдельного, более медленного UX-потока (взаимодействие с
    аутентификатором на каждое разворачивание).
  * **Решение этого документа**: на Web SMK кэшируется в `IndexedDB`,
    ЗАШИФРОВАННЫЙ ключом сессии (не самим SMK — раздел 2.2 `K_wrap` для
    другого случая), и это **явно, вслух объявляется человеку слабее**, чем
    на нативных платформах — тем же способом, каким продукт уже честно
    объявляет отсутствие подписи macOS-сборки (`/macos-warning`) вместо
    молчания. WebAuthn/PRF — опциональный апгрейд для браузеров, которые его
    поддерживают, не обязательное требование фазы 1 (§18).
  * Практическое следствие: на Web разлогин ДОЛЖЕН очищать закэшированный
    SMK из `IndexedDB` (в отличие от нативных платформ, где кэш в
    Keychain/Keystore переживает logout намеренно, §11) — потому что
    сохранение материала в origin-читаемом, не hardware-backed хранилище
    дольше необходимого — необоснованный лишний риск именно на этой
    платформе.

## 4. Подключение нового устройства (device onboarding)

1. Вход (Яндекс ID или magic-link) — без изменений, как сегодня.
2. Клиент запрашивает `GET /api/v1/vault/sync-key` (новый эндпоинт, §12).
   * Если для аккаунта ещё нет синк-ключа (первое устройство вообще) —
     см. §2.2: генерация, установка пароля восстановления, загрузка обёртки.
   * Если уже есть — сервер отдаёт `wrapped_sync_key` + соль + проверочный
     блоб. Дальше — экран «Введите пароль восстановления» (одноразово на это
     устройство — не на каждый вход).
3. Клиент выводит ключ обёртки локально (Argon2id по присланной соли),
   проверяет по проверочному блобу, разворачивает синк-ключ, кэширует его в
   защищённом хранилище (§3). Готово — устройство синхронизируется как
   любое другое.
4. Неверный пароль — троттлинг (§3), без ограничения числа устройств,
   которые можно ПОПРОБОВАТЬ подключить (троттлинг — по попыткам ввода
   пароля, не по числу устройств).

Ключевое свойство конструкции: онбординг **не требует какого-либо
асимметричного обмена ключами между устройствами** (в отличие от Signal/
Matrix, где у каждого устройства свой ключ и нужен ratchet/cross-signing).
Здесь один и тот же симметричный синк-ключ разворачивается на каждом
устройстве независимо из одного и того же пароля восстановления — продукту
не нужна модель «несколько получателей», у заметок один автор и его же
устройства.

## 5. Синхронизация между несколькими устройствами

Из конструкции §1 и §4 следует бесплатно: раз все устройства аккаунта держат
ОДИН и тот же синк-ключ, `ZapiskiCloudBackend` на любом устройстве
шифрует/расшифровывает одними и теми же байтами ключа — никакой отдельной
логики многопользовательской синхронизации не требуется, `SyncEngine`
(очередь, diff3, CRDT-слияние, конфликт-копии) работает ровно как сегодня,
потому что видит расшифрованные байты сразу после границы (§1).

Единственное новое условие гонки: устройство A могло не пройти онбординг
(§4) раньше, чем устройство B успело что-то отправить. Это не хуже сегодняшней
ситуации «устройство ещё не вошло в аккаунт» — синк с него просто не пойдёт,
пока онбординг не пройден, точно как сегодня синк не идёт без входа в
аккаунт вовсе.

## 6. Политика восстановления пароля/ключа

Один пароль восстановления — единственная точка отказа, и это стоит явно
признать, а не полагаться, что человек его не забудет. Предлагается
опциональный ВТОРОЙ путь восстановления, тем же приёмом «двойной обёртки»,
которым пользуются 1Password/Bitwarden:

* При создании SMK (§2.3) человеку **однократно** показывается код
  восстановления. Тем же Argon2id/AES-GCM код разворачивает ОТДЕЛЬНУЮ,
  ВТОРУЮ обёртку того же SMK, независимую от обёртки пароля восстановления.
* Обе обёртки хранятся на сервере параллельно — сервер по-прежнему не может
  прочитать ни одну: обе непрозрачны.
* Потеря пароля — код восстановления открывает SMK и позволяет установить
  новый пароль (переобернуть). Потеря кода — пароль продолжает работать как
  единственный путь.
* Потеря ОБОИХ — синк для новых устройств недоступен навсегда (§2.3,
  состояние 5). Локальные копии на уже подключённых устройствах не страдают.

Это опция, а не обязательное требование этого документа: без второго пути
восстановления архитектура тоже работает, просто с одной точкой отказа
вместо двух. Решение о том, ПРЕДЛАГАТЬ ли его вообще — за владельцем
продукта (открытые вопросы, §17.2). Но раз closure-pass явно потребовал,
чтобы КОД восстановления был инженерным, а не только продуктовым решением
(«не только продуктовый вопрос — инженерия обязана зафиксировать минимум
энтропии, генерацию CSPRNG, контрольную сумму, формат представления
отдельно от требования к энтропии»), ниже — та часть, которая не ждёт
решения продукта.

### 6.0. Код восстановления — инженерный минимум (не продуктовое решение)

Четыре решения ниже — фиксированные требования этого документа. То, что
ОСТАЁТСЯ продуктовым решением — только видимое человеку представление
(разбивка на группы, использование слов вместо символов) поверх уже
зафиксированной здесь энтропии, а не вместо неё.

1. **Минимум энтропии — 128 бит.** Код НЕ вводится и не запоминается
   человеком многократно (в отличие от пароля восстановления) — он
   генерируется машиной один раз и читается один раз при создании. Поэтому
   для него нет компромисса «удобно запомнить vs безопасно», который
   оправдывал бы низкую энтропию: 128 бит уже делает прямой перебор
   вычислительно невозможным (2^128 ≈ 3.4×10^38) независимо от скорости
   KDF — в отличие от §6.1, где энтропия ЧЕЛОВЕЧЕСКОГО пароля восстановления
   и есть узкое место. Продукт волен поднять до 256 бит ради запаса
   (стоимость — более длинная строка для переписывания), но НИЖЕ 128 бит
   опускаться нельзя ни при каком представлении.
2. **Генерация — только платформенный CSPRNG, только на устройстве.**
   `crypto.getRandomValues(new Uint8Array(16))` (тот же примитив, что уже
   используется для соли и nonce в `util/bytes.ts`, `randomBytes`) — НИКОГДА
   не `Math.random()`, не производная от пароля, не производная от `Date.now()`
   или `device_id`. Генерируется в момент создания SMK (§2.3, состояние
   «Создан») и никогда не хранится на сервере в развёрнутом виде — только
   производная от него обёртка, тем же путём, что и пароль восстановления
   (Argon2id код → ключ обёртки → AES-GCM оборачивает SMK).
3. **Контрольная сумма — обязательна, для обнаружения опечатки ДО обращения
   к серверу.** 128 бит случайных байт человек будет переписывать от руки —
   транспозиции и опечатки типичны. `checksum = SHA-256(код)[0:2]` (16 бит)
   добавляется к отображаемому представлению. При вводе клиент пересчитывает
   контрольную сумму ЛОКАЛЬНО: несовпадение — это опечатка, а не неверный
   код, и сообщается мгновенно, без похода на сервер и без прогона
   Argon2id (дорогого по конструкции, §6.1) — и, что важнее, БЕЗ расхода
   попытки из троттлинга неверных попыток (§3): опечатка — не попытка
   подбора, и не должна тратить бюджет `unlockDelayMs`.
4. **Формат представления — отдельное решение, поверх уже зафиксированной
   энтропии.** 128 бит энтропии + 16 бит контрольной суммы = 144 бита для
   отображения. Безопасный вариант по умолчанию — Crockford Base32
   (32-символьный алфавит без визуально спутываемых `0`/`O`, `1`/`I`/`L`),
   сгруппированный блоками по 4–5 символов через дефис — не требует
   вычитанного и локализованного словаря, которого сегодня в кодовой базе
   нет. Словарный формат (диалектика, BIP39-подобный, на русском) остаётся
   открытым продуктовым улучшением (§17.2) — он читаемее, но требует
   отдельной работы по подбору/вычитке словаря (уникальные приставки для
   автодополнения, отсутствие оскорбительных слов, однозначная морфология)
   и не блокирует фазу 1.

## 6.1. Оффлайн-атака на пароль восстановления — модель угрозы и параметры

Closure-pass явно потребовал признать это explicitly: «сервер хранит
обёрнутый синк-ключ + соль/параметры KDF → скомпрометированный сервер даёт
возможность офлайн-подбора пароля восстановления». Первая версия документа
этого не формулировала — риск был неявным следствием §3, а не названной
угрозой. Формулируется здесь прямо.

### 6.1.1. Модель угрозы

Актёр «скомпрометированный сервер синка» (THREAT-MODEL §2.2, §14 ниже)
получает при компрометации: `wrapped_sync_key` (AES-GCM шифротекст SMK),
Argon2id-соль, параметры KDF (открыто в схеме — они ДОЛЖНЫ быть открытыми,
иначе устройство не сможет их применить) и проверочный блоб. Это ровно тот
набор данных, которого достаточно для ОФЛАЙН перебора пароля восстановления
— без единого запроса к серверу, а значит **без какого-либо действия
троттлинга** (`unlockDelayMs`, §3, — он существует только на пути «через
сервер», а после утечки данных атака идёт локально у атакующего). Это
стандартный, хорошо изученный класс угрозы («master password + KDF + wrapped
secret на сервере» — тот же класс, что у Bitwarden/1Password), и он не
устраняется полностью НИКАКИМ выбором параметров KDF — только замедляется.
Единственный способ закрыть его совсем — не хранить обёртку на сервере
вовсе, что противоречит самой цели «восстановить синк на новом устройстве
без другого доверенного устройства под рукой» (§4).

### 6.1.2. Из чего это следует практически

1. Пароль восстановления обязан требовать РЕАЛЬНОЙ энтропии при создании —
   не «минимум 8 символов» (это ловится словарной атакой за секунды даже
   под Argon2id), а оценка энтропии на вводе (zxcvbn-подобная метрика или
   аналог, уже возможно есть прецедент в других формах продукта — сверить
   при реализации) с явным отказом принимать пароль ниже порога.
2. Продукту стоит явно, в UI, обозначить два пути восстановления РАЗНОЙ
   силы, а не подавать их как эквивалентные: **код восстановления (§6.0)
   — настоящая защита, невзламываемая независимо от того, что случится с
   сервером; пароль восстановления — удобство, чья реальная сила равна
   тому, что человек выбрал**. Честная формулировка в интерфейсе — тот же
   принцип, который уже применён в этом закрытии к тексту письма входа
   (`mailer.ts`) — не обещать больше, чем есть на самом деле.
3. Замедление офлайн-подбора — единственный рычаг инженерии. Ниже —
   конкретные параметры.

### 6.1.3. Параметры Argon2id

Базовая точка — уже принятые в продукте параметры для пароля vault'а
(`ARGON2_PARAMS`, `crypto/provider.ts`): RFC 9106, второй рекомендованный
набор, `t=3, m=64 МиБ, p=4`. Это одновременно (а) уже реализовано и
протестировано на всех трёх платформах через `hash-wasm`, (б) следует
рекомендации OWASP Password Hashing Cheat Sheet «максимизировать память в
пределах приемлемой задержки», что и есть основная защита от
GPU/ASIC-параллелизма для атакующего.

* **Целевая задержка — интерактивный бюджет ~0.5–1 с** на входе на новое
  устройство (§4), на САМОМ СЛАБОМ разумно поддерживаемом устройстве
  каждой платформы — не на топовом.
* **Единый набор параметров по умолчанию для всех платформ** — `t=3, m=64
  МиБ, p=4` (переиспользуется буквально, не выводится заново). Это НЕ
  автоматически синоним «столько же безопасности везде» — важное уточнение
  ниже про WASM.
* **Абсолютный минимальный пол — НИКОГДА не ниже `t=2, m=19 МиБ, p=1`**
  (минимальный параметр набор, который сам RFC 9106/OWASP признают
  допустимым для интерактивного входа при ограниченной памяти). Если
  бенчмарк слабого устройства покажет, что даже эти параметры не
  укладываются в приемлемую задержку — это повод чинить производительность
  (WASM-путь, воркер вместо главного потока), а не опускать параметры ещё
  ниже.
* **Запрет тихого понижения.** Если платформе всё же приходится
  использовать пониженный (но не ниже пола) набор параметров, это ДОЛЖНО
  фиксироваться в самом контейнере — тем же способом, каким уже версионируется
  контейнер заметки (`CONTAINER_VERSION`/`ARGON2_PARAMS`, bump версии при
  смене параметров, `crypto/container.ts`). Какие параметры реально
  применены к КОНКРЕТНОЙ обёртке — должно быть читаемо из самой обёртки, а
  не предполагаться по умолчанию. Это и есть требование «не отключать
  строгость молча ради удобства» в применении к KDF-параметрам.

### 6.1.4. Бенчмарки — что нужно измерить перед реализацией, а не сейчас

Этот документ фиксирует ТРЕБОВАНИЕ к бенчмаркам, а не выдуманные числа —
реальные цифры получаются прогоном на устройствах, это работа
реализации, не ревью:

* **Android** — на представительном НЕДОРОГОМ устройстве (не топ линейки:
  квота продукта ориентируется на массовое устройство, не на флагман),
  `hash-wasm` (подтверждено: нативного Rust-пути Argon2 в `apps/mobile/
  src-tauri` нет — WASM работает и здесь, не только в браузере).
* **Web/WASM** — в Chrome и Safari на аналогично слабом железе. WASM
  типично на 2–4× медленнее нативного кода — не измеренная здесь оценка, а
  общее свойство WASM, которое надо ПОДТВЕРДИТЬ бенчмарком конкретно для
  `hash-wasm`, а не принять как данность.
* **Windows/macOS (Tauri)** — тоже `hash-wasm` (тот же вывод: отдельного
  нативного Argon2-пути на десктопе сегодня нет), значит десктоп НЕ
  получает автоматического преимущества нативной скорости над вебом,
  вопреки интуиции «десктоп быстрее браузера» — тоже требует измерения, а
  не предположения.
* Результат бенчмарка — это то, что решает вопрос §6.1.3 «нужен ли
  пониженный, но не ниже пола, набор параметров для какой-то платформы» —
  до бенчмарка это открытый вопрос, а не готовое число.

## 7. Зашифрованные метаданные и то, что утечкой останется

Честный список того, что сервер продолжит видеть **даже после** этой работы
— и что закрывается, а что нет.

**Закрывается полностью:**
* Содержимое заметки (текст, тело версии, тело CRDT-апдейта) — единственная
  вещь, ради которой всё затевается.

**Закрывается — путь метаданных, минимальный вариант (фаза 1, §18):**
* `blobs.path` перестаёт быть человекочитаемым: клиент кладёт туда
  анонимизированный/случайный идентификатор вместо реального пути
  (`Личное/Дневник 12 марта.md` → непрозрачная строка). Дерево папок
  (порядок, вложенность, названия папок) переносится в отдельный
  ЗАШИФРОВАННЫЙ «манифест vault'а» — один блоб, который клиент сам собирает
  и расшифровывает локально, сервер его не интерпретирует, как не
  интерпретирует и содержимое заметок. `path_hash` при этом теряет смысл как
  «хеш реального пути» и либо убирается, либо становится детерминированной
  меткой поиска: `HMAC(K_manifest, реальный_путь)` — доменным подключом
  манифеста (§2.2), НЕ SMK напрямую (SMK не используется ни для чего, кроме
  вывода доменных подключей, §2.1) — та же логическая заметка на разных
  устройствах аккаунта даёт ту же метку, но инвертировать её без ключа
  нельзя (стандартный приём «детерминированное шифрование для ключа
  поиска», применяется ТОЛЬКО к этому одному полю, не к содержимому).

**Закрывается полностью — вариант с изменением схемы (фаза 2, опционально,
§18):** `blobs`/`versions` переходят на адресацию по `note_id`, как уже
сегодня устроены `crdt_updates`/`versions.note_id` — колонка `path`
убирается из Postgres вовсе, а не просто анонимизируется.

**НЕ закрывается — остаётся видимым серверу, и это стоит признать прямо,
а не молчать:**
* Размер шифротекста (≈ размер заметки, ± накладные расходы контейнера).
* Время создания/изменения (`mtime`, `taken_at`, `created_at`) и частота
  правок — нужны серверу для сортировки, `?since=`-курсоров, квоты, списания
  версий по сроку.
* `device_id` каждого CRDT-апдейта — нужен для причины «кто внёс правку» в
  истории версий (`VersionSnapshot.source`), без него пропадает полезная
  часть UX истории версий, а не только приватность.
* Число заметок, общий объём (нужен для квоты §7 ТЗ).
* Адрес почты аккаунта — не относится к содержимому заметок, ортогонален
  этой работе (аутентификация, не хранилище).
* Сам факт, что аккаунт вообще пользуется Облаком Записок, и с какого IP —
  как у любого сетевого сервиса; это уже названная и явно принятая как «вне
  модели» категория (см. THREAT-MODEL §4, если она перечисляет
  network-metadata — сверить и держать формулировку согласованной при
  реализации).

Это тот же стиль честной записи остаточного риска, которым уже пользуется
THREAT-MODEL.md §2.2 — при реализации предлагается ДОПОЛНИТЬ, а не переписать
этот раздел ровно этим списком.

## 8. Шифрование CRDT-логов, истории версий и стратегия нонса AES-GCM

Оба потока проходят через ТУ ЖЕ границу (§1), поэтому отдельного
криптографического примитива не требуют — только подтверждение, что оба
пути действительно проходят через `ZapiskiCloudBackend.put/get`, а не через
что-то в обход, и, ГЛАВНОЕ (closure-pass отклонил первую версию именно
здесь), формально доказанная схема нонса.

### 8.0. Что было отклонено и почему

Первая версия документа предлагала «не случайный нонс на каждый апдейт, а
монотонный счётчик, замешанный с `device_id`» без дальнейшей формализации.
Заказчик справедливо указал: «монотонный счётчик + device_id» сам по себе
недостаточен — не определены 96-битная раскладка, поведение после
переустановки, персистентность счётчика, восстановление из бэкапа,
столкновение между устройствами, взаимодействие с ротацией ключа,
максимальное число инвокаций. Это не мелочи: монотонный счётчик,
СБРОШЕННЫЙ после переустановки (новый экземпляр приложения на том же
устройстве — обычный случай) при ТОМ ЖЕ ключе — классический сценарий
повторного использования нонса, который для AES-GCM катастрофичен (раскрывает
XOR двух открытых текстов и ломает аутентификацию). Ниже — не патч этой
схемы, а другая, формально более простая и **проверяемо безопасная**
альтернатива.

### 8.1. Решение: случайный 96-битный нонс, безопасность — через доменное разделение ключей (§2), а не через состояние

**Схема:** `nonce = crypto.getRandomValues(new Uint8Array(12))` — ЧИСТО
случайные 96 бит на КАЖДОЕ шифрование, без какой-либо встроенной структуры
(без битов счётчика, без битов `device_id`). Тот же примитив, что уже
используется и протестирован для локального шифрования заметки
(`encrypt()`, `crypto/provider.ts:162`, `randomBytes(NONCE_LENGTH)`) —
НИКАКОГО нового кода для генерации нонса не требуется, только его
переиспользование на уровне синка.

**Почему это безопасно, а не просто «то же самое, только без счётчика»:**
NIST SP 800-38D §8.3 даёт формальную границу для случайных 96-битных IV —
при не более чем **2^32 инвокаций под одним ключом** вероятность коллизии
нонса остаётся ≤ 2^-32 (пренебрежимо мала). Ключевой ход конструкции — §2.2
(доменное разделение + деривация ПО ЗАМЕТКЕ) даёт КАЖДОЙ заметке СОБСТВЕННЫЙ
`K_crdt`, а не один ключ на весь аккаунт. Оценка бюджета для самого частого
потока — CRDT-апдейтов одной заметки:

```
1 апдейт / 2 с непрерывно, 24/7, 10 лет ≈ 10 × 365 × 24 × 3600 / 2
                                        ≈ 1.58 × 10^8 ≈ 2^27.2
```

Это на ПЯТЬ порядков (2^32 / 2^27 ≈ 32×) ниже безопасной границы NIST даже
для нереалистично интенсивного использования одной заметки одним аккаунтом
за десятилетие. Ни одна другая доменная пара (content, versions, manifest,
wrap — §2.2) не приближается к этому порогу и близко: они на порядки реже.

### 8.2. Прямые ответы на каждый пункт, который потребовал заказчик

* **96-битная раскладка нонса.** Плоские 96 случайных бит, без внутренней
  структуры — сознательное решение: структура (биты счётчика/device_id)
  нужна ТОЛЬКО если полагаться на неё для уникальности; здесь уникальность
  даёт случайность и малый бюджет инвокаций (§8.1), а не структура нонса.
* **Уникальность нонса для одного ключа.** Обеспечена статистически —
  граница NIST выше, с запасом в 32×.
  на конкретный уровень интенсивности использования одной заметки (§8.1).
* **Поведение после переустановки приложения.** НЕ ВЛИЯЕТ. У чисто
  случайного нонса нет состояния, которое можно потерять при
  переустановке, — каждый следующий нонс независимо случаен вне
  зависимости от истории устройства. Это прямое улучшение относительно
  отклонённой схемы, для которой переустановка была ГЛАВНОЙ уязвимостью.
* **Персистентность счётчика.** Счётчик инвокаций по (заметка, домен)
  всё же стоит вести — НЕ как часть нонса, а как ADVISORY-метрика для
  превентивной ротации (§8.3 ниже). Его потеря — деградация UX
  (пропущенное напоминание о ротации), НЕ событие безопасности: в отличие
  от отклонённой схемы, он не участвует в конструкции нонса вовсе.
* **Rollback/восстановление из бэкапа.** НЕ ВЛИЯЕТ, тем же аргументом, что
  и переустановка: откат состояния устройства назад не может заставить
  генератор случайных чисел повторить прошлый нонс — каждый вызов
  `crypto.getRandomValues` независим от локальной истории.
* **Коллизия между устройствами.** Уже учтена в границе NIST: оценка
  2^32-инвокаций — это ОБЩИЙ бюджет для всех энкодеров под одним ключом
  вместе, не «на устройство». Несколько устройств аккаунта, независимо
  шифрующих под одним и тем же `K_crdt` заметки, — ровно тот сценарий,
  который граница уже покрывает, без какой-либо координации между ними.
* **Ротация ключа.** После ротации SMK (§2.3, §11) ВСЕ доменные подключи
  выводятся заново из нового SMK — новый ключ означает совершенно новое,
  никак не связанное с прошлым пространство нонсов. Переиспользование
  нонса между старым и новым ключом невозможно по построению (разные ключи
  → GCM-безопасность не требует согласования нонсов между ними вовсе).
* **Максимальное число инвокаций.** Формальный предел — 2^32 (граница
  NIST). Эксплуатационный порог ротации — см. §8.3.

### 8.3. Эксплуатационный порог: превентивная ротация, а не жёсткий отказ

Хотя реалистичный бюджет (§8.1) на порядки ниже границы NIST, конструкция
всё равно фиксирует явный, консервативный порог: **2^28 (≈268 млн)
инвокаций на пару (заметка, домен)** — в 16 раз ниже формальной границы
2^32. При достижении порога клиент проактивно инициирует ротацию ТОЛЬКО
доменного подключа этой заметки (не всего SMK — точечная ротация одного
`K_crdt` возможна, если завести версию домена в `info`, например
`zapiski/sync/v1/crdt/<note_id>/<epoch>`, и увеличивать `epoch` при
исчерпании; решение о необходимости этого механического усложнения — уже
implementation detail, не архитектурное). Счётчик, ведущий этот порог, —
тот самый advisory-счётчик из §8.2, и его потеря (переустановка) в худшем
случае откладывает ротацию, но не создаёт уязвимости — граница NIST всё
ещё на порядок выше эксплуатационного порога.

### 8.4. Потоки

* **CRDT-апдейты** (`crdt_updates.ciphertext`, `CrdtStore`,
  `engine.ts:777-786`) — сегодня уходят на `backend.put()` как обычные байты
  без шифрования, несмотря на имя колонки. После этой работы шифруются
  `K_crdt` заметки (§2.2), нонс — по схеме §8.1.
* **История версий** (`versions.storage_key` → тот же `BlobStore`) —
  шифруется `K_versions` заметки (§2.2), тем же `backend.put`, что и обычная
  заметка, нонс — по той же схеме §8.1 (частота на порядки ниже, граница
  NIST не приближается вовсе).

## 9. Разрешение конфликтов над зашифрованным содержимым

Уже решено конструкцией §1: **сервер никогда не сливает ничего, ни сегодня,
ни после этой работы.** Слияние (diff3, CRDT three-way merge,
`SyncEngine.merge()`) как проходило на устройстве по открытому тексту, так и
продолжает — потому что граница шифрования стоит НИЖЕ слияния (в
`ZapiskiCloudBackend`), а не внутри него.

Единственный НОВЫЙ конфликтный случай — не текстовый, а ключевой: два
устройства аккаунта разошлись в том, каким синк-ключом шифруют (например,
одно из них не подтянуло ротацию §2.3 после смены ключа кем-то ещё). Это не
«конфликт содержимого», а «нечитаемый чужой шифротекст» — и для него
конструкция уже предлагает готовое поведение: та же ветка, что сегодня
обслуживает `isEncryptedPath` (`engine.ts:762`, «зашифрованные — автослияние
невозможно, сохраняем обе», BEHAVIOR §5.4) — расширяется с «путь оканчивается
на `.md.enc`» на «расшифровка синк-ключом не удалась», и делает то же самое:
сохраняет обе версии рядом, как конфликт, вместо попытки нечестного
слияния. Новой ветки логики придумывать не нужно — расширяется условие
входа в уже существующую.

## 10. Миграция существующих незашифрованных облачных заметок

Однократный проход после первого успешного онбординга SMK на устройстве
(§4). Первая версия документа описывала порядок операций (пункты 1–4 ниже)
подробно, но НЕ давала полного перечня мест, где сегодня лежит открытый
текст, — closure-pass потребовал именно этот перечень, каждый пункт
отдельно, и честного признания там, где мгновенное стирание физически
невозможно. Ниже — то же самое, что было, плюс §10.1 (полный перечень мест)
и §10.2 (честная политика бэкапов).

1. Источник истины — локальный vault (invariant #1), не то, что уже лежит в
   облаке. Проход идёт ПО ЛОКАЛЬНЫМ файлам, переотправляя их через уже
   шифрующий `ZapiskiCloudBackend.put()` — то есть просто «синк с нуля»
   тем же механизмом, которым сегодня синхронизируется первое подключение
   нового устройства с пустым локальным индексом, только в обратную
   сторону (не скачать, а перезалить).
2. Старая открытая версия по тому же (или, после фазы 2 §7 — старому)
   идентификатору перезаписывается новой зашифрованной — тот же
   REST-путь `PUT`, что и обычное сохранение, ничего специального на
   сервере не требуется для содержимого.
3. Требование к порядку: новая зашифрованная копия должна быть подтверждена
   записанной ДО того, как что-либо трогает старую — типовое правило любой
   миграции без потери данных, тот же принцип, каким уже пользуется
   `crypto/notes.ts` (`encryptNoteFile`: сначала пишет `.md.enc`, только
   потом стирает `.md`).
4. Проход обязан быть возобновляемым (прерывание сети/приложения на
   середине большого vault'а — обычный случай на мобильном интернете, не
   исключение) — курсор «докуда дошли» персистентно на устройстве, не в
   памяти.

### 10.1. Полный перечень мест хранения открытого текста — что закрывается и как

Миграция обязана доказуемо убрать открытый текст не только из «основной
записи», а из КАЖДОГО места ниже. Проверено по факту (миграции, код),
не предположено:

| Место | Сегодня | После миграции | Как проверено |
|---|---|---|---|
| `blobs` (текущее содержимое) | открытый текст | шифротекст | пункт 2 выше |
| `versions` (история версий) | открытый текст | шифротекст `K_versions` | тот же `BlobStore.put`, §8.4 |
| `crdt_updates.ciphertext` | открытый текст, несмотря на имя колонки | шифротекст `K_crdt` | §8.4 |
| `blobs`/`versions`, помеченные `deleted_at` (надгробия) | файл в томе стирается СРАЗУ при мягком удалении (комментарий в `0002_vault.sql`) | то же поведение, уже достаточное — стирание тома не зависит от того, зашифрован файл или нет | схема миграции 0002, п. 5 первой версии документа, подтверждено чтением `server/migrations/0002_vault.sql` |
| Файловая система сервера (том `blobs`) | содержит расшифрованные — то есть попросту исходные — байты, адресованные по SHA-256 шифротекста (сегодня шифротекста НЕТ, поэтому адресация по хешу открытого текста) | после миграции адресация по хешу РЕАЛЬНОГО шифротекста; старые файлы физически удаляются томом при `deleted_at`, не просто помечаются | тот же путь, что и удаление обычного blob'а — новой процедуры не требуется |

| Очереди | На сервере отдельной очереди задач нет (только HTTP-маршруты и БД); на клиенте есть офлайн-очередь синка (`sync/queue.ts`) — она ЛОКАЛЬНАЯ, хранит несинхронизированные правки на устройстве человека (invariant #1, всегда открытым текстом локально — это ожидаемо и не является утечкой), и после реализации отправляет их через уже шифрующую границу (§1) при следующей попытке синка | локальная очередь не меняется по конструкции; отправленные из неё байты — шифротекст | архитектурное следствие §1 |
| Бэкапы сервера | **см. §10.2 — честно: сегодня их нет вовсе** | — | §10.2 |

### 10.2. Бэкапы — честная политика, а не выдуманная задним числом

Проверено по факту: в `deploy/docker-compose.yml` Postgres использует
обычный Docker-том (`zapiski_db_data`) без какого-либо `pg_dump`/
`pg_basebackup`/cron-задачи резервного копирования — ни в конфигурации
деплоя, ни в документации `deploy/`, ни где-либо ещё в репозитории.
**У продукта сегодня нет формальной политики резервного копирования
Postgres или тома `blobs` вообще** — то, что может существовать на уровне
инфраструктуры хостинг-провайдера (снэпшоты диска и т.п.), не
задокументировано и не находится под контролем этого проекта.

Это меняет ответ на вопрос closure-pass «опишите РЕАЛЬНУЮ политику
хранения/устаревания бэкапов, поскольку мгновенное стирание из
исторических бэкапов обычно невозможно»: раз задокументированных бэкапов
нет, то и остаточного риска «расшифрованные исторические копии в бэкапах»
у этой миграции сегодня тоже нет — но только пока это правда. Это ДОЛЖНО
быть явно занесено как условие, а не молчаливое допущение:

* Если/когда появится формальная политика бэкапов Postgres или тома
  `blobs` (реализация этого проекта её не предполагает, но инфраструктурные
  решения меняются независимо), эта миграция автоматически перестаёт быть
  полной: старые открытые бэкапы, снятые ДО миграции, продолжат содержать
  открытый текст до истечения их собственного retention-периода — и
  единственный честный способ закрыть это ПОЛНОСТЬЮ — ротация SMK (§2.3),
  после которой даже утечка СТАРОГО бэкапа раскрывает данные, зашифрованные
  СТАРЫМ ключом, но новый трафик и новые бэкапы уже под новым.
* Требование к реализации: прежде чем заводить резервное копирование
  Postgres/`blobs` (отдельная, не входящая в этот документ работа), обязана
  быть зафиксирована retention-политика (сколько бэкапов хранится, как
  долго) — именно потому, что «мгновенное стирание из бэкапа» технически
  недостижимо, и продукту нужно явное число, а не молчаливое «как-нибудь
  само сотрётся».
* Это не блокирует фазу 1 (§18): отсутствие бэкапов сегодня — не преграда
  для миграции, а честная запись остаточного риска НА БУДУЩЕЕ, ровно тем же
  стилем, каким §7 уже фиксирует остаточные метаданные.

## 11. Выход из аккаунта / отзыв устройства

Существующая инфраструктура `device_id`/сессий (после SEC-029) уже отвязывает
сессию конкретного устройства от остальных. Этого достаточно для «выйти —
эта сессия больше не обменивается токенами», но **не** для «это устройство
больше не может прочитать то, что синхронизируется дальше» — симметричный
общий синк-ключ, однажды закэшированный в Keychain/Keystore устройства,
переживает разлогин локально, пока его не сотрёт ОС или переустановка. Это
не упущение, а то же ограничение, что у любой схемы с одним общим
симметричным ключом на все устройства (тот же класс ограничения, что у
Signal/WhatsApp при «unlink device» — старое устройство хранит то, что уже
получило, до этого момента).

Честные два уровня действия, оба стоит предложить в UI отдельно, не путая:

* **«Выйти» (logout)** — отзывает токены сессии этого устройства. Дёшево,
  уже почти построено.
* **«Это устройство больше не моё» (revoke + ротация ключа)** — logout ПЛЮС
  ротация SMK (§2.3): новый случайный ключ (и все выведенные из него
  доменные подключи, §2.2 — заново), новая обёртка паролем восстановления,
  полный перешифровальный проход (тем же механизмом, что миграция §10)
  поверх ВСЕГО содержимого аккаунта на всех ещё доверенных
  устройствах. Дорогая операция (трафик, время), поэтому явно ДРУГАЯ кнопка,
  не синоним обычного выхода — и явно с предупреждением о цене (объём
  данных, которые нужно перезалить).

## 12. Изменения на сервере

Минимально необходимый набор, без миграции path→id (то есть фаза 1, §18):

* **Новый эндпоинт** `GET/PUT /api/v1/vault/sync-key` — хранит и отдаёт
  `wrapped_sync_key` (и, если реализуется §6, вторую обёртку кодом
  восстановления) + публичную соль Argon2id + проверочный блоб. Всё поле —
  непрозрачные байты для сервера, тот же принцип, что уже описывает
  `crdt_updates.ciphertext`. Переиспользует уже существующую
  аутентификацию/`device_id`-мидлварь маршрутов `/api/v1/vault/*` — новой
  схемы авторизации не требуется.
* **Новая таблица или колонки** для хранения этой обёртки (одна строка на
  аккаунт, не на устройство и не на заметку) — маленькая, отдельная от
  `blobs`.
* **`crdt_updates`/`versions`** — схема НЕ меняется (фаза 1): колонки уже
  готовы принять шифротекст, клиенту достаточно начать его туда класть.
* **`blobs.path`** — фаза 1 не требует миграции схемы: клиент просто
  перестаёт класть туда человекочитаемую строку (см. §7). `path_hash`
  пересматривается по необходимости при реализации.
* **Копия письма/интерфейса**, утверждающая «Заметки мы не читаем —
  технически не можем» (`server/src/services/mailer.ts:97`) — сегодня это
  ложное утверждение для аккаунта, который не шифрует явно. Дешёвая правка,
  доступная НЕЗАВИСИМО от всей остальной работы и НЕ являющаяся заменой ей:
  смягчить формулировку («если вы включите шифрование заметки, мы технически
  не сможем её прочитать») до того момента, как утверждение станет верным
  для всех безусловно.

## 13. Обратная совместимость

Старая версия приложения, ничего не знающая про синк-ключ, обратившись к
аккаунту, который уже прошёл онбординг (§4), получит от `GET` на существующий
путь заметки шифротекст ТАМ, где раньше был открытый текст, — и без версии
API это будет молча показано человеку как «заметка сломалась», а не как
«обновите приложение». Это должно быть явной, а не подразумеваемой частью
дизайна:

* Признак «аккаунт синхронизируется с шифрованием» должен быть виден клиенту
  ДО того, как он получит зашифрованные байты, не постфактум — например,
  полем ответа на `GET /api/v1/vault/sync-key`, которое старый клиент вообще
  не запрашивает и потому не видит вовсе.
* Раскатка — по аккаунту, не мгновенно и не принудительно для всех сразу:
  аккаунт остаётся «нешифрованным» до первого добровольного онбординга синк-
  ключа на любом его устройстве, ровно как сегодня добровольно опциональность
  §3.3 по заметке. Это снимает риск «старый клиент сломался у всех разом» —
  ломается только у того, кто явно включил шифрование НА КАКОМ-ТО устройстве,
  а на других поставлена СТАРАЯ версия приложения (сценарий редкий, но не
  нулевой — телефон обновляется автоматически, десктоп может отставать).
* Практическое смягчение: как только один клиент видит признак «аккаунт
  шифруется», он обязан отказаться синхронизировать эту заметку понятным
  сообщением («обновите приложение»), а не показать шифротекст как есть.
  Нужна проверка версии приложения — если в контракте (`platform`,
  версии сборки — уже передаются на `/api/v1/auth/magic-link`, см.
  `PLATFORMS`) уже есть основа для такой проверки, реализация должна на неё
  опереться, а не изобретать отдельный канал версии.

## 14. Модель угроз — что меняется в THREAT-MODEL.md §2.2

Не переписывается сейчас (документ проектный, без правок кода и без правок
других документов) — но фиксируется, какая правка потребуется, когда
реализация будет готова:

* Актёр «Скомпрометированный сервер синка» теряет способность «читать...
  содержимое» как БЕЗУСЛОВНУЮ (сегодня — «Может: читать... всё, что лежит в
  его томе и базе»). После реализации это сужается до содержимого заметок
  ТЕХ аккаунтов, что не прошли онбординг синк-ключа (переходный период §13),
  и до списка метаданных из §7 этого документа — который и должен занять
  место сегодняшней фразы «сервер синка назначает не только байты, но и
  пути» (это как раз §7 закрывает, частично или полностью, по фазе).
* «Остаточный риск — критический и незакрытый» (сегодняшняя формулировка)
  меняется на список §7 «НЕ закрывается» — то есть риск не исчезает
  полностью, а становится ТЕМ остаточным риском, какой стоило бы иметь у
  любого облачного синка метаданных, а не критическим провалом обещания.

## 15. Приёмочные тесты zero-knowledge — что они обязаны проверять

Без кода — описание критериев, а не реализация:

1. **Расширение `security.zero-knowledge.test.ts`** (или аналог на новом
   месте): перехватить КАЖДЫЙ `PUT`, который `SyncEngine` направляет в
   `ZapiskiCloudBackend` для аккаунта, прошедшего онбординг синк-ключа —
   утверждать, что тело запроса НЕ содержит открытый текст заметки НИ
   подстрокой (не только «не равно», подстрокой — иначе тест не ловит
   частичную утечку). То же для `path`/`path_hash`, отправляемых на
   сервер — не равны и не содержат подстрокой человекочитаемое название
   заметки.
2. **`schema.zero-knowledge.test.ts` — продолжение той же идеи**: не только
   форма схемы (нет колонки под открытый текст), но и ФАКТИЧЕСКОЕ содержимое
   после реального прогона синка тестовой заметки — высокая энтропия байтов
   в `crdt_updates.ciphertext`/`blobs`-файле, а не читаемый JSON/markdown.
3. **Тест «чужой ключ не открывает чужой аккаунт»**: два независимых
   `WebCryptoProvider`/синк-ключа (эмуляция двух аккаунтов) синхронизируются
   с одним и тем же тестовым сервером — ключ аккаунта А не расшифровывает
   ничего из блобов аккаунта Б, даже подобранный из тех же исходных байтов
   (например, случайно совпавшая соль — маловероятно, но тест обязан не
   полагаться на вероятность, а доказывать фактом).
4. **Тест «неверный пароль восстановления»**: троттлинг срабатывает (тот же
   `unlockDelayMs`, что уже покрыт тестами для vault-пароля), сервер не
   отдаёт частично развёрнутый ключ ни в каком виде, попытка не оставляет
   след настоящего пароля восстановления в логах (тот же принцип, что уже
   проверяет `privacy.logging.test.ts` для магик-линков).
5. **Тест миграции (§10)**: старая открытая запись реально пропадает и из
   БД, и из тома (файл, не только строка) после успешной перезаписи
   зашифрованной версией — не раньше, чем зашифрованная версия подтверждена
   записанной (порядок операций, не только конечное состояние).
6. **Тест обратной совместимости (§13)**: старый клиент (эмулируется
   отсутствием запроса `sync-key`/старым `platform`) на аккаунте, прошедшем
   онбординг, получает понятный отказ синхронизации этой заметки, а не
   шифротекст, показанный как текст.

## 16. Явно НЕ входит в это решение

* «Просто спрятать Cloud» — см. вводный абзац; допустимо ТОЛЬКО как
  временный kill-switch на время, пока эта работа не готова, не как замена
  ей.
* Многополучательское шифрование (шаринг заметки с другим человеком,
  публикация с отдельным ключом для читателя) — сегодняшняя функция
  публикации (`server` publish-роуты) вне объёма: она и задумана как
  публичная страница, не секрет, ортогональна этому документу.
* Regular/scheduled ротация синк-ключа «по расписанию» — только по
  требованию человека (§11), не автоматическая политика; если понадобится
  позже, конструкция это позволяет (тот же путь, что device-revoke), но не
  запрашивается сейчас.
* Шифрование метаданных ДО последнего байта (полностью скрыть даже размер,
  даже частоту правок) — сознательно вне объёма, тот же класс компромисса,
  что уже принят в THREAT-MODEL.md для других актёров; не решается в этом
  документе как «нерешаемое дёшево», а не как «неважное».

## 17. Открытые вопросы — решение за владельцем продукта

1. **Фаза 1 (анонимизация `path`) vs фаза 2 (полная миграция на
   `note_id`-адресацию) — что фазой 1, что фазой 2, или сразу фаза 2?**
   Рекомендация инженерной стороны — фаза 1 первой (дешевле, без миграции
   схемы, закрывает содержимое сразу), фаза 2 отдельным проектом. Решение —
   продуктовое (скорость выхода против полноты закрытия).
2. **Представление кода восстановления (§6.0)** — минимум энтропии (128
   бит), генерация (CSPRNG на устройстве) и контрольная сумма — теперь
   инженерное требование, не открытый вопрос (closure-pass). Открытым
   остаётся только ВИЗУАЛЬНОЕ представление ПОВЕРХ этого минимума: группы
   Crockford Base32 по умолчанию (§6.0, пункт 4) или отдельная работа по
   вычитанному русскому словарю слов — вопрос дизайна интерфейса и объёма
   работы, не безопасности.
3. **WebDAV/Яндекс.Диск — тоже под обязательное синк-шифрование, или это
   остаётся «собственное хранилище человека, его выбор»?** (§1). Граница
   класса это позволяет решить независимо и позже.
4. **Раскатка** — принудительно всем аккаунтам разом или добровольный
   онбординг с переходным периодом (§13 предполагает второе как более
   безопасное для обратной совместимости, но это тоже решение владельца, не
   инженерии).
5. ~~**Публиковать ли kill-switch (скрытие Cloud) прямо сейчас**~~ —
   **решено и реализовано.** `CLOUD_SYNC_ENABLED = false`
   (`packages/core/src/cloud-sync.ts`), проверено тестом
   (`packages/app/test/cloud-kill-switch.test.tsx`): новым людям Облако не
   предлагается, у кого уже было включено — переподключение отказывает и
   честно объясняется, а не продолжает молча слать открытый текст.
6. **Формальная политика резервного копирования сервера (§10.2)** — новый
   вопрос этой ревизии: сегодня её нет вовсе, и это временно снимает
   остаточный риск «расшифрованные копии в старых бэкапах». Если/когда
   владелец продукта заведёт резервное копирование Postgres/`blobs`, он
   обязан одновременно зафиксировать retention-период — это решение за
   пределами данного документа, но данный документ требует, чтобы оно было
   принято ЯВНО, а не по умолчанию.

## 19. Implementation plan — небольшие TDD-коммиты (фаза 1)

Требование closure-pass: «отдельный implementation plan SEC-001 по
небольшим TDD-коммитам» — не реализация, а план, по которому реализация
начнётся ПОСЛЕ приёмки этого документа. Каждый пункт — один или несколько
коммитов размера, сравнимого с P1-фиксами этого же closure-pass (падающий
тест → минимальный код → фальсификация через `git stash` реализации →
подтверждение RED по нужной причине → возврат → GREEN → typecheck →
коммит). Порядок — зависимости, а не приоритет: пункт N предполагает, что
N−1 уже слит.

1. **`packages/core/src/crypto/sync-keys.ts` — HKDF-деривация доменных
   подключей от SMK.** Чистая функция(и) над уже существующим
   `WebCryptoProvider`/`deriveKey` (§2.2): `deriveContentKey(smk, noteId)`,
   `deriveCrdtKey(smk, noteId)`, `deriveVersionsKey(smk, noteId)`,
   `deriveManifestKey(smk)`, `deriveWrapKey(smk)`. Тесты: разные `note_id`
   дают криптографически различные ключи (шифрование одного и того же
   текста разными подключами не расшифровывается чужим); один и тот же
   `(smk, note_id, domain)` детерминированно даёт один и тот же ключ на
   двух независимых вызовах (нужно для многоустройственности, §5). Никакой
   сети, никакого UI — чистая криптография, самый безопасный первый коммит.
2. **`packages/core/src/crypto/sync-keys.ts` — генерация и обёртка SMK
   паролем восстановления.** `generateSmk()` (`crypto.getRandomValues(32)`),
   `wrapSmk(smk, recoveryPassword)`/`unwrapSmk(wrapped, recoveryPassword)`
   поверх уже существующего `deriveMasterMaterial`/Argon2id (§3, §6.1.3
   параметры). Тесты: неверный пароль возвращает `null`, а не бросает (тот
   же принцип, что и `decrypt()` заметки, BEHAVIOR §5.2); `unlockDelayMs`
   применяется тем же приёмом, что и для пароля vault'а.
3. **Код восстановления (§6.0).** `generateRecoveryCode()` (CSPRNG 128 бит +
   контрольная сумма), `formatRecoveryCode()`/`parseRecoveryCode()`
   (Crockford Base32, группировка). Тесты: контрольная сумма ловит
   однобуквенную опечатку/транспозицию БЕЗ обращения к серверу; энтропия
   кода — 128 бит фактическая, не только заявленная (статистический тест на
   распределение, не полное доказательство, но регрессия против «забыли
   вызвать CSPRNG»).
4. **Сервер: таблица + эндпоинт `GET/PUT /api/v1/vault/sync-key` (§12).**
   Миграция БД (новая таблица, одна строка на аккаунт — не на устройство,
   не на заметку), маршрут, авторизация через существующий
   `device_id`-мидлварь. Тест: непрозрачность поля для сервера
   (`schema.zero-knowledge.test.ts`-подобный — высокая энтропия байт,
   не JSON), доступ только владельцу аккаунта.
5. **`ZapiskiCloudBackend` — граница шифрования (§1, §2.2).** Оборачивание/
   снятие обёртки в `put()`/`get()`/`pushUpdates()`/`pullUpdates()` доменным
   подключом по типу объекта (`content`/`crdt`/`versions`/`manifest`) и
   `note_id` из пути. Нонс — по схеме §8.1 (просто `randomBytes(12)`,
   никакого нового примитива). Тест: `security.zero-knowledge.test.ts`
   расширяется — тело КАЖДОГО исходящего запроса не содержит открытый текст
   заметки НИ ПОДСТРОКОЙ (уже сформулировано в §15, пункт 1).
6. **Онбординг устройства (§4) — клиентская логика без UI.**
   `SyncKeyOnboarding` (или аналогичное имя) — состояние
   «нет SMK на сервере / есть, нужен пароль / развёрнут, кэшировать».
   Платформенный порт `biometrics.enroll` для non-Web (§3.1) — новый
   `ключ_id`. Тест: полный цикл на подставном `fetch` + подставном
   `biometrics`, без реального UI-экрана ещё.
7. **Web-хранилище SMK (§3.1) — отдельно от общего порта.** `IndexedDB`,
   обёрнутый ключом сессии, очистка при логауте. Тест: логаут действительно
   стирает запись; материал недоступен без активной сессии.
8. **UI онбординга/настроек** — экраны «Введите пароль восстановления»,
   показ кода восстановления один раз, обновление `SettingsScreen.tsx`
   (снятие ограничений kill-switch'а — этот коммит и есть момент, когда
   `CLOUD_SYNC_ENABLED` переключается на `true`, НЕ раньше пункта 12).
   Существующие тесты kill-switch'а (`cloud-kill-switch.test.tsx`) на этом
   шаге ЦЕЛЕНАПРАВЛЕННО обновляются, а не удаляются — они начинают
   проверять НОВОЕ поведение включённого флага, тем же файлом, с тем же
   именем сценариев там, где применимо.
9. **Миграция уже загруженных открытых заметок (§10).** Проход по
   локальному vault'у, курсор возобновляемости, порядок «новая шифрованная
   подтверждена записанной, только потом трогаем старую». Тест:
   прерывание на середине (эмуляция сети) не теряет данные и возобновляется
   с курсора, а не с начала.
10. **Анонимизация `blobs.path` (§7, минимальный вариант) + шифрованный
    манифест vault'а.** Клиент собирает/расшифровывает манифест локально
    ключом `K_manifest`; сервер хранит и отдаёт его как непрозрачный блоб.
    Тест: `blobs.path`, отправляемый на сервер, не содержит и не равен
    человекочитаемому имени заметки/папки (§15, пункт 1, распространённый
    на путь).
11. **Обратная совместимость — версия-гейт (§13).** Признак «аккаунт
    зашифрован» на `GET /api/v1/vault/sync-key`; старый клиент получает
    понятный отказ синхронизации вместо шифротекста, показанного как текст.
    Тест: эмуляция старого клиента (нет запроса `sync-key`) получает отказ,
    не мусор.
12. **Разрешение конфликтов над шифротекстом (§9).** Расширение условия
    входа в существующую ветку `isEncryptedPath` на «расшифровка доменным
    подключом не удалась». Тест: расхождение ключей на двух устройствах
    сохраняет обе версии, не пытается слить.
13. **Полная приёмка (§15) + включение флага.** Все пункты §15 прогоняются
    реально (не только модульно — сквозной сценарий «два устройства,
    реальный тестовый сервер»), `CLOUD_SYNC_ENABLED = true`
    (пункт 8 выше уже подготовил UI). Обновление THREAT-MODEL.md §2.2
    (§14 этого документа). Отдельная приёмка перед снятием kill-switch'а —
    не автоматическое следствие «код написан».

Пункты 2–13 зависят от пункта 1; пункты 6–8 могут идти параллельно с 9–12
после пункта 5 (независимые ветки работы, общая зависимость — только
готовая граница шифрования). Ротация SMK (§2.3, §11 полностью) и revoke-с-
ротацией как отдельная UI-кнопка в этот план фазы 1 сознательно НЕ входят —
фаза 2 (§18), собственная последовательность коммитов, отдельное решение
владельца о сроках.
