# Архитектура КОМПАС.ЗАПИСКИ — инженерный контракт

Документ обязателен к соблюдению всеми, кто пишет код в этом репозитории.
При расхождении с ТЗ приоритет: `docs/spec/BEHAVIOR.md` > `docs/spec/SCREENS.md`
> `docs/spec/DESIGN_TOKENS.md` > `docs/spec/README.md` > этот документ.

## 1. Как достигается «одинаковый сквозной функционал»

Требование заказчика — Android, Windows и веб с **идентичным** функционалом.
Оно выполняется не дисциплиной, а строением репозитория:

```
packages/core     ← вся логика: vault, индекс, поиск, CRDT, крипто, синк, импорт/экспорт
packages/ui       ← токены тем + библиотека компонентов
packages/editor   ← CodeMirror 6 live-preview
packages/app      ← ВСЕ экраны и всё поведение (единственное место, где есть UI-логика)
  ↑ всё вышеперечисленное платформо-независимо и не знает, где исполняется

apps/web          ← тонкая оболочка: монтирует <App/>, даёт VaultStorage поверх FSA/OPFS
apps/desktop      ← тонкая оболочка: Tauri 2, даёт VaultStorage поверх нативной ФС
apps/mobile       ← тонкая оболочка: Tauri 2 Android, тот же VaultStorage
server            ← KompasCloud API
```

**Правило.** В `apps/*` не должно быть ни одного экрана, ни одной кнопки, ни
одной строки продуктовой логики. Только: точка входа, реализация платформенных
портов и платформенный манифест. Экран, добавленный в `apps/web`, но не в
`apps/mobile`, — это ровно тот дефект, из-за которого провалился Android
Obsidian. Такой код не принимается.

## 2. Платформенные порты

Единственное, чем платформы различаются. Объявлены в `@zapiski/core/platform`.

```ts
interface VaultStorage {
  read(path: string): Promise<Uint8Array | null>;
  write(path: string, data: Uint8Array): Promise<void>;   // атомарно: tmp + rename
  remove(path: string): Promise<void>;
  rename(from: string, to: string): Promise<void>;
  list(dir: string): Promise<VaultEntry[]>;
  stat(path: string): Promise<VaultStat | null>;
}

interface PlatformCapabilities {
  biometrics: BiometricProvider | null;   // Android Keystore / Windows Hello / WebAuthn-PRF
  haptics: HapticProvider | null;         // §0 BEHAVIOR — только Android
  secureFlag(on: boolean): void;          // FLAG_SECURE, §5.3 BEHAVIOR
  globalHotkey: GlobalHotkeyProvider | null;  // только Windows
  shareTarget: ShareTargetProvider | null;    // только Android
  updater: UpdaterProvider | null;            // desktop + Android
}
```

Возможности, которых на платформе нет, равны `null` — и UI **скрывает**
соответствующий элемент, а не показывает его выключенным
(`BEHAVIOR.md` §5.1: «Если платформа не поддерживает — тумблер скрыт, не
„выключен и недоступен“»).

## 3. Незыблемые инварианты

Нарушение — блокирующий дефект на приёмке.

1. **File over app.** Источник истины — `.md` на диске. Индекс — производная,
   удаление `.zapiski/` не теряет ни одной заметки.
2. **Local-first.** Приложение полностью работает без сети и без аккаунта.
   Ни один экран основного сценария не требует авторизации.
3. **Zero-knowledge.** На сервер уходят только зашифрованные байты. Открытый
   текст заметки не покидает устройство никогда.
4. **Ни одного hex вне токенов.** Проверяется `scripts/lint-tokens.mjs` в CI.
5. **Ни одной строки, зашитой в компонент.** Только каталоги i18n (`ru`, `en`).
6. **Ни одного SMS-зависимого пути.** Прямой запрет ТЗ §5.5.
7. **Слова «Сохранить» в UI нет нигде.** Автосохранение: debounce 500 мс + blur.
8. **Деструктив отменяем.** 6-секундный тост «Отменить» либо корзина 30 дней.
   Диалог подтверждения разрешён ровно в трёх местах (`BEHAVIOR.md` §0).
9. **Ошибка никогда не блокирует ввод текста.**
10. **Тексты ошибок — дословно** из реестра `BEHAVIOR.md` §11.

## 4. Перф-бюджеты (автотесты, не пожелания)

| Бюджет | Где проверяется |

| FTS <50 мс на 10 000 заметок | `packages/core/test/perf.test.ts` |

## 5. Правила совместной работы

* Каждый пакет владеет своим каталогом. Не редактировать чужой — если нужен
  экспорт, запросить его у владельца через интерфейс.
* Публичный API пакета — только через `src/index.ts`. Глубокие импорты
  (`@zapiski/core/src/internal/...`) запрещены.
* Новый компонент вводится, только если ни один существующий не подходит,
  и сначала описывается в `docs/spec/COMPONENTS.md` (требование ТЗ §6).

## 6. Документация — часть определения готовности

Документация ведётся в трёх контурах и обновляется **в том же изменении**, что
и код. Изменение, меняющее поведение продукта и не трогающее документацию, не
принимается.

| Контур | Каталог | Для кого | Кто обновляет |
| --- | --- | --- | --- |
| Разработческая | `docs/dev/` | Разработчик, который придёт после нас | Автор изменения |
| Продуктовая | `docs/product/` | Продукт, маркетинг, поддержка | CPO |
| Пользовательская | `docs/user/` | Пользователь продукта | Техписатель |

Отдельно и неизменно: `docs/spec/` — исходное ТЗ (не редактируется),
`docs/adr/` — архитектурные решения, `ARCHITECTURE.md` и `ACCEPTANCE.md`.

**Правило честности документации.** Документируется то, что есть в коде, а не
то, что запланировано. Функция из ТЗ, ещё не реализованная, помечается явно.
Документация, описывающая несуществующее поведение, — дефект: разработчик
примет её за готовое, а пользователь не сможет по ней работать.

Что обязано обновляться при изменении:

* поменялся публичный API пакета → `docs/dev/modules/<пакет>.md`;
* появился или изменился эндпоинт → `docs/dev/modules/server.md`;
* изменилось видимое пользователю поведение → соответствующий файл в
  `docs/user/` и строка в `docs/product/changelog.md`;
* изменился состав функций → `docs/product/scope.md` и `roadmap.md`;
* принято архитектурное решение вразрез с ТЗ §2.2 → новый ADR.
